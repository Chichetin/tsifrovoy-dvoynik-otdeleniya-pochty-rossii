# GIT.md — правила ведения Git

Цель: `main` в любой момент — рабочий кандидат на сдачу (редактор открывается,
демо-планы загружаются, тесты зелёные), а сданную версию можно однозначно восстановить.

Правило: **закончил одно логическое действие — проверь, закоммить и запушь ветку.**

## Ограничение сервера

Репозиторий на GitLab хакатона. **Прямой push в `main` запрещён для всех команд** —
ветка защищена организаторами. В `main` изменения попадают только через Merge Request,
merge делает участник команды в GitLab (права есть у всех). Push в `main` не пробовать:
он отклоняется сервером и дополнительно закрыт в `permissions.deny`.

## Автономность агента

Агент коммитит и пушит **свою ветку сам, без запроса подтверждения**, как только шаг
закончен и проверки зелёные, и создаёт MR в `main`. Это постоянное разрешение на
проект; технически оно задано в `.claude/settings.json` (`permissions.allow`), а
`permissions.deny` закрывает всё, что переписывает историю или сгребает чужую работу.

Разрешение опирается на проверки, а не отменяет их:

- перед коммитом и push — `git fetch --prune` и просмотр обеих сторон расхождения;
- в коммит попадает только текущий шаг: `git add <явные пути>`. Никогда `git add -A`,
  `git add .`, `git commit -a` — даже если так написано в инструкции организаторов: в
  дереве может лежать незакоммиченная работа другого участника или другой сессии;
- `--force`, `rebase` и `amend` опубликованного, `reset --hard`, `clean` — только по
  явной просьбе человека. Удаление веток и worktree агент делает сам, но только по
  правилам из «Уборка»;
- секреты, `.env`, `node_modules`, сборки и логи не коммитятся (см. `.gitignore` и
  Stop-хук `check-secrets.sh`).

## Worktree по умолчанию

Основная копия (`/home/ir6/my/tsifrovoy-dvoynik-otdeleniya-pochty-rossii`, ветка `main`)
— не рабочее место агента. В ней могут параллельно сидеть человек и другие сессии, и
незаконченная правка одного ломает запуск и тесты остальным. Поэтому **любая задача,
меняющая файлы, делается в своём worktree на своей ветке**.

Старт:

```bash
# Claude Code — сессия сразу открывается в .claude/worktrees/<поток>-<тема>
# на ветке worktree-<поток>-<тема>
claude -w <поток>-<тема>

# Уже запущенная сессия или другой агент (Codex и т. п.) — те же путь и ветка руками:
git fetch --prune
git worktree add .claude/worktrees/<поток>-<тема> -b worktree-<поток>-<тема> origin/main
```

`.claude/worktrees/` в `.gitignore`. `claude -w` копирует файлы из `.worktreeinclude`
(`.env`) из основной копии; при `git worktree add` руками `.env` копировать самому.
`node_modules` и `.venv` в новом worktree нет — поставить заново.

Организаторы в примере называют ветки `feature/<имя>`; это пример, а не требование.
Ветки `worktree-<поток>-<тема>` оставляем: их создаёт `claude -w`, и на них опираются
правила уборки.

## Финиш: ветка → Merge Request → main

```bash
# 1. проверки зелёные, коммит только своих путей
git fetch --prune
git merge origin/main              # если main ушёл вперёд; после merge — тесты заново
# 2. push ветки и создание MR в main одной командой (push options GitLab)
git push -u origin HEAD \
  -o merge_request.create \
  -o merge_request.target=main \
  -o merge_request.title="<поток>: <что закончено>"
```

GitLab печатает ссылку на MR в выводе push — её агент пишет человеку и в `HANDOFF.md`.
Push options на сервере хакатона работают (проверено 2026-09-16, MR !1). Повторный push
в ту же ветку обновляет открытый MR, новый не создаёт.

3. **Merge — в GitLab.** Без squash и без rebase: обычный merge-коммит, иначе правило
   уборки «нет коммитов сверх `origin/main`» перестаёт работать. Мержит либо человек в
   веб-интерфейсе, либо агент командой `bash scripts/gitlab-mr.sh merge <iid>` —
   токен со scope `api` получен 16.09, скрипт берёт его из credential helper и в
   репозиторий не пишет. Скрипт отказывается сливать MR с конфликтами и MR не в
   состоянии `opened`.
4. После merge, в основной копии, когда там никто не работает:
   `git -C /home/ir6/my/tsifrovoy-dvoynik-otdeleniya-pochty-rossii pull --ff-only`.
5. Уборка — см. ниже.

Мелкие шаги одной задачи копятся в той же ветке и том же MR: новый push обновляет
открытый MR. Долго не мержить не нужно — MR живёт часы, а не дни.

### Уборка

Агент убирает за собой сам. Ветку или worktree можно удалить, только если **оба**
условия выполнены (так удаление ничего не теряет):

1. ветка влита: `git fetch --prune && git rev-list --count origin/main..<ветка>` → `0`;
2. ветка не открыта ни в одном worktree, кроме твоего собственного, а в твоём нет
   незакоммиченного: `git worktree list`, `git -C <путь> status --porcelain` → пусто.
   Worktree другой сессии не удаляется, даже чистый и «пустой»: сессия могла только
   начать работу.

```bash
git worktree remove .claude/worktrees/<поток>-<тема>   # без --force
git branch -D worktree-<поток>-<тема>                  # после проверки п. 1
git push origin --delete worktree-<поток>-<тема>       # если GitLab не удалил её при merge
git worktree prune
```

Свой worktree убирать из основной копии (`git -C /home/ir6/my/tsifrovoy-dvoynik-otdeleniya-pochty-rossii …`),
а не изнутри него. Чужой worktree с незакоммиченными изменениями или ветку с невлитыми
коммитами не трогать никогда — даже если она выглядит заброшенной: спросить человека.

Без worktree, прямо в основной копии, можно только:

- чтение, анализ, запуск тестов и `jury` без правок;
- `git pull --ff-only` после merge.

Всё, что меняет файлы, включая одну строку в `HANDOFF.md`, идёт через ветку и MR:
закоммитить в `main` локально нельзя — такой коммит некуда запушить.

## Доступ к GitLab

Токен участника (`ir6.edu`) хранится в `~/.git-credentials` (`credential.helper store`
в конфиге репозитория) и никогда не печатается и не попадает в чат. Он пускает в git
(push, fetch), но **не в API** (`/api/v4/user` → 401, проверено 2026-09-16), поэтому
merge через API агенту недоступен.

## Перед началом работы

```bash
git fetch --prune
git status -sb
git log --oneline HEAD..origin/main   # что пришло от команды
git log --oneline origin/main..HEAD   # что есть только у нас
```

Если чужой коммит пересекается с задачей — сначала прочитать diff. Перед тем как
назвать что-то дефектом, убедиться, что ветка не `behind`.

## Коммиты

Формат: `<поток>: <что закончено>`, сообщение на русском.

| Префикс | Поток |
|---|---|
| `editor:` | 2D-редактор: холст, инструменты, выделение, перемещение, поворот, UI |
| `model:` | модель данных, справочники, инвентаризация, геометрия, проверки корректности |
| `store:` | сохранение, загрузка, формат файла, бэкенд |
| `ai:` | ИИ-ассистент: расчёт рекомендаций, промпты, клиент LLM |
| `3d:` | упрощённое 3D-представление |
| `demo:` | демо-проект: исходный и изменённый план, ZIP, скриншоты для презентации |
| `infra:` | деплой, Docker, CI, зависимости, настройки Claude Code, Git |
| `docs:` | README, условия, решения, справки |
| `fix:` | исправление, если поток смешанный |

Один коммит — один осмысленный шаг. Трейлеры соавторства ИИ (`Co-Authored-By`,
`Claude-Session`, «Generated with Claude Code») в коммиты и MR не добавляем.

## Ветки и ревью

- `main` — редактор запускается, тесты зелёные, демо-планы открываются.
- Ветка задачи — `worktree-<поток>-<тема>`; крупная или рискованная (формат
  сохранения, модель данных, `.claude/`) — ревью другим участником в MR до merge.
- Force-push запрещён везде.

## Сдача и теги

Сданную версию тегировать **после** проверки по скиллу `submission-checklist`, на
commit из `origin/main`:

```bash
git fetch --prune
git tag -a submit-final origin/main -m "Сдача: <commit>, демо пройдено <дата>"
git push origin submit-final
```

Не ставить тег заранее. Если сервер запрещает push тегов — записать commit hash сдачи
в README и `HANDOFF.md`.

## Безопасный откат

| Ситуация | Действие |
|---|---|
| Посмотреть историю | `git log --oneline --decorate --graph` |
| Вернуть свой файл | `git restore <path>` после просмотра diff |
| Отменить влитый коммит | `git revert <hash>` в новой ветке → MR |
| Посмотреть старое состояние | `git switch --detach <tag-or-hash>` |
