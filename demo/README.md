# Демо-комплект: как открыть планы заново

Это часть 2 сдачи — собственный демо-проект команды. Всё здесь **синтетическое**:
отделение придумано и нарисовано в нашем редакторе, реальных планов БТИ, адресов,
ФИО, телефонов и табельных номеров в файлах нет.

## Что в комплекте

| Файл | Что это |
|---|---|
| `before.json` | исходный план отделения (формат редактора, 8 зон, 53 объекта) |
| `after.json` | тот же план после применения рекомендации ассистента |
| `recommendation.json` | рекомендации ассистента целиком: факты, `id`, правила, допущения |
| `effect.md` | эффект «было → стало» человеческим языком, числа из расчёта |
| `README.md` | этот файл |

## 1. Открыть готовый план (основной вход)

Проверяющему ничего рисовать не нужно: сервис открывается с уже размеченным планом.

1. Открыть сервис (адрес — в корневом `README.md` репозитория) **или** запустить
   локально:

   ```bash
   npm ci
   npm run dev          # http://127.0.0.1:5173
   ```

2. Выбрать **«Файл → Открыть существующий»** в шапке и выбрать `before.json` из этого комплекта.
3. Что должно появиться сразу:
   - на плане — L-образное помещение 132,00 м², 8 зон, включая вложенные
     «Зона ожидания» и «Зона очереди» внутри «Клиентского зала»;
   - в панели **«Инвентаризация»** — 53 объекта с типами, зонами и инвентарными
     номерами; **«Показать все (53)»** разворачивает весь перечень;
   - в панели **«Проверка»** — 1 ошибка и 1 предупреждение (так и задумано:
     их чинит рекомендация ассистента, см. `effect.md`);
   - слой **«Тепловая нагрузка зон»** — «Зона очереди» (`z_queue`) с загрузкой
     100 % помечена «перегружена», остальные зоны ниже порога;
   - нажать название предмета в перечне — откроется **карточка свойств**: тип, координаты,
     поворот, зона и атрибуты из справочника (например, у `eq_10` — «Номер окна» 1,
     инвентарный номер `ИНВ-ДЕМО-010`).
4. Так же открывается `after.json` — это изменённый вариант. В нём 54 объекта,
   есть `eq_54` «Скамья ожидания 2», а панель проверки пуста.

Оба файла открываются той же кнопкой, что и пример организаторов
`example_plan.json`: формат распознаётся по содержимому файла.

## 2. Повторно сохранить и открыть заново

1. Открыть `before.json`, изменить что-нибудь (например, в карточке свойств
   поменять «Название» или координаты X/Y).
2. Нажать **«Сохранить»** в шапке — браузер скачает JSON-файл плана.
3. Перезагрузить страницу и открыть скачанный файл: геометрия, зоны, оборудование,
   `id`, атрибуты и связи «объект → зона» те же, правка на месте.

## 3. Создать план с нуля (второй вход)

Пункт **«Файл → Создать новый»** даёт пустое помещение 12 × 9 м. Дальше: инструмент «Зона» —
обвести зону, библиотека слева — выбрать тип оборудования и кликнуть по плану,
карточка свойств — задать атрибуты, «Файл → Экспорт → JSON» — получить такой же файл, как
`before.json`.

## Откуда взялись эти планы

`before.json` рисуется в интерфейсе нашего редактора. Браузерный тест
`tests/e2e/open-demo.spec.ts` (#204) повторяет это руками: «Файл → Создать новый» →
внешний контур → три перегородки → шесть проёмов → восемь зон с типом и названием →
первые объекты из библиотеки. Сохранённый файл совпадает с `before.json`: контур,
стены, проёмы, зоны с вложенностью, `id` объектов и их положение. `id` стен, проёмов
и зон редактор выдаёт свои (`w_7`, `z_3`), тест сопоставляет их по порядку.

Чтобы файл пересобирался байт в байт, скрипт `demo/build.ts` пишет его **теми же
командами редактора** (`applyCommand`). Зоны объектов считает та же функция
`relations.reconcile`, что и при перетаскивании мышью. Исходник плана —
`demo/plan-source.ts`: контур, стены, проёмы, зоны и оборудование в метрах.

```bash
npx tsx demo/build.ts     # пересобрать before.json, after.json, recommendation.json, абзац effect.md
npx tsx --env-file=.env demo/build.ts   # то же с провайдером LLM из .env → "mode": "llm"
npm run package:demo      # собрать один ZIP комплекта → output/demo/ops-digital-twin-demo.zip (в git;
                          # после любой правки demo/ пересобрать и закоммитить — tests/demo.test.ts сверяет)
npm test -- tests/demo.test.ts                  # проверки комплекта
DEV_PORT=5176 CI=1 npx playwright test tests/e2e/demo.spec.ts   # открытие в браузере
```

Шаги, которыми получен `after.json` (ровно те же руками в редакторе — это
проверяется браузерным тестом `tests/e2e/demo.spec.ts`):

1. Спросить ассистента про оборудование зон → он находит нехватку скамьи в
   `z_waiting`.
2. Спросить место для скамьи в `z_waiting` → поставить скамью из библиотеки в
   найденную точку (2,20; 2,00), заполнить название и атрибуты в карточке.
3. Спросить место для терминала очереди в `z_entrance` → перенести существующий
   `eq_1` в найденную точку (7,90; 2,10), задав X и Y в карточке.
4. «Файл → Экспорт → JSON» — скачанный файл и есть `after.json`.

## Известные ограничения комплекта

- Режим, в котором объяснена рекомендация, записан сборщиком в поле `mode` файла
  `recommendation.json` и в абзаце `effect.md`: `llm` — код причины, вариант и факты
  выбрала модель (провайдер, модель и дата — в поле `llm`), выбор прошёл проверку
  кодом; `fallback` — расчёт с шаблонным объяснением (штатный режим, D-016), причина
  — в поле `fallbackReason`. Структура рекомендации и все числа от режима не
  меняются.
- Правила комплектования `rule_bench_min` и `rule_info_display_max` — **допущения
  команды** из `data/catalog/rules.json`, а не нормативы Почты России. Правило
  «терминал очереди не далее 3 м от входа» взято из перечня оборудования
  организаторов и потому считается ошибкой, а не предупреждением.
- Значения `loadPercent`, `staffCount`, `queueLength` у зон — синтетические числа
  для информационных слоёв, их никто не измерял.
- Поиск места проверяет геометрию (помещение, зона, стены, другое оборудование на
  той же высоте), но не ширину прохода, эргономику и доступность маршрута.
