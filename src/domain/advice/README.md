# src/domain/advice

Поиск размещений, комплектование, сравнение планов, проверка объяснений и шаблоны.

**Владелец:** поток 4. **Пакеты:** A01 A02 A03 A04.

## Граница модуля

Потребляет contracts и публичные функции geometry/relations/metrics/catalog/inventory. Никаких API-ключей или вызовов LLM.

**Уместность зоны (D-186).** `zoneFit` в `placement.ts`: уместные типы зон — из правил
комплектования `count` с заданным `min` (в том числе `0`) **и** из текущей расстановки
(где объекты этого типа уже стоят). Сужается только тип с правилом-минимумом; правило
только с `max` — потолок, а не «дом»; объекты с `occupiesFloor: false` не сужаются.
Сверяются две зоны места: самая глубокая зона, где лежит весь след (`zoneId`), и самая глубокая зона под центром (`centreZoneId`). Обе должны быть уместны. Подпись варианта — `placementZonePath`: «Клиентский зал → Зона ожидания». Текущая расстановка — эвристика: она подтверждает сама себя и не доказывает нормативную уместность, поэтому ответ прямо называет её основанием. Нет правила — ищем везде и говорим
об этом; нет зон в плане — уместность не проверяется; явно выбранная неподходящая зона —
выбор человека с пометкой; уместной зоны нет — пустой ответ с объяснением. Зоны вариантов
попадают в `refs` рекомендации.

**Бюджет поиска (D-221).** `maxCells` ограничивает сырой обход ограничивающего прямоугольника, а `maxProbes` расходуется только на клетки внутри уместных зон и геометрические проверки. Поэтому пустая часть большой вогнутой зоны не даёт ложный ответ «места нет», а патологически большой план всё равно не блокирует запрос.

**Покрытие камерами (D-306, задача #32).** `camera-coverage.ts`: `cameraCoverage(plan, representation)` —
доля клиентских зон, видимая хотя бы одной камерой слоя «Камеры и зоны обзора». Сетка 0,25 м,
центр квадрата в зоне и в секторе (`pointInViewSector`), итог без двойного счёта вложенных зон,
слепые пятна — полосами по строкам. Клиентская зона — `isClientZone`: атрибут `publicAccess`,
иначе умолчание типа зоны, иначе родитель. **Допущение расчёта:** сектор строится по углу и
дальности из атрибутов камеры (пустые — умолчания слоя), стены и мебель его не режут, видео не
подключается — это оценка для планирования, а не паспорт устройства. Допущение идёт в
рекомендации ассистента, а не пометкой в интерфейсе слоя (D-281).

**Камера на слепое пятно (D-308, задача #32).** `camera-placement.ts`: `calculateAdvice` для типа,
который рисует слой-сектор (`ot_camera`), без точки на плане идёт в `cameraPlacementAdvice`, если
в клиентских зонах (или в выбранной клиентской зоне) есть слепое пятно. Пятно — самый большой
4-связный участок невидимых квадратов; точки через 0,5 м внутри клиентских зон (грубее при переборе
больше 2 млн проверок), повороты через 15°; ранг — число квадратов пятна в секторе. До трёх вариантов
не ближе 1 м, каждый проходит `validatePlan`. Рекомендация — обычный `place` с фактами контракта;
эффект в процентах пересчитывает `cameraCandidateEffect` из плана и кандидата — для `assumptions`,
фактов чата (`coverage.percent`, единица `percent`, изменение в п. п.) и текста без LLM; кешируется на объект плана и варианта. Слой камер ответ называет словами — действие «включить слой» изменило бы ревизию и погасило «Применить». Нет
клиентских зон, нет пятна, зона не клиентская или указана точка — обычный `findPlacements`.
`placement.ts` для этого экспортирует `verify`, `reserveId`, `issueKey`. Пробный объект типа — `objectOfType` из `domain/commands`.

**Место для стоящего объекта (#177).** `relocation.ts`: `findRelocations(plan, { objectId, zoneId, anchor? })`
ищет место без самого объекта, с его размером и контуром; места ближе `minSeparation_m` к текущему
не считаются (`searchPlacements`, `avoid`). Перенос — одна команда `object.put` с тем же `id` и
атрибутами, без новых ошибок `validatePlan`. До трёх переносов и последним «оставить как есть» с теми
же показателями: зоны, правила, зазор до стены, факты `comparePlans`, площадь и объекты зон, покрытие
камерами. В чате — `find_place` с `objectId`, переносы — предложения правок (`relocationProposal`).
