# src/features/assistant

Запрос сценария, карточки рекомендаций, before/after, preview и fallback.

**Владелец:** поток 4. **Пакеты:** A06.
Это место для реализации; пока здесь размещена только карта модуля.

## Граница модуля

Потребляет contracts и domain/advice для локального fallback; fetch только к своему /api/advice. Ключи и прямые вызовы провайдера запрещены.
Серверный 429 ограничивает вызовы модели, но не лишает пользователя расчёта:
`advice-client.ts` пересчитывает рекомендации в браузере и явно помечает режим
«Без LLM». Ошибки 400/422 остаются ошибками плана или запроса.
В «Комплектовании» панель показывает название типа оборудования и зоны из
справочника текущего плана рядом с проверенными числами рекомендации.
В «Найти место» у каждого варианта названа его зона — имя из плана
(`data-testid="candidate-zone"`), либо «вне зон» (D-186); голого `id` в подписи нет.
У «Ссылок» и «Изменений» карточки подпись и `title` кнопки — имя сущности
(`title="Показать на плане · id <id>"`), а `id` ещё и виден без DevTools: под ними —
раскрытие «ID зон и объектов» со списком `<code>id</code> — имя» на все `refs` и
`changes.ref` рекомендации (D-320/D-322/D-323, #10, объяснимость — CLAUDE.md «ИИ-ассистент»).
В чате (`AgentChat.tsx`) id зоны или объекта, который код вписал в ответ, браузер сам
превращает в кнопку с именем сущности (тот же `title`), а под ответом — то же
раскрытие «ID зон и объектов» по `answer.refs` — для клавиатуры и без клика по каждому
упоминанию в тексте. Id типа или правила (не зона и не объект) на кнопку не
переводится — предложение остаётся как его написал расчёт, id в тексте виден (review
!318): такую фразу сокращает только `hideNamedIds` (D-321) — там, где у текста нет
своего клика по каждому упоминанию (например, «Ограничения» карточки).
Необязательное пожелание пользователя (D-222) модель использует только для выбора
среди уже рассчитанных кодов причины и вариантов. Оно не расширяет расчёт и не может
добавить число или факт; без LLM панель прямо пишет, что пожелание не учитывалось.

## Отдельный исходный файл (#5)

ComparisonPanel в сценарии «Эффект изменений» показывает таблицу buildPlanComparison. useComparisonSource читает источник через readPlanFile и защищает от поздних ответов, не обращаясь к store. App передаёт источник сценарию compare и очищает его при открытии/новом документе. Исходный файл не меняет save baseline/dirty/undo; чат сохраняет собственную точку отсчёта. Для разных ID планов только сводные показатели и предупреждение, сценарный запрос отключён. Список изменений включает предметы, зоны, слои и помещение, но не стены/проёмы/справочник.

## Лист согласования (#35)

Кнопка «Лист согласования…» в `ComparisonPanel` (рядом с «Сравнить с файлом…») открывает
`ApprovalSheet.tsx` — печатную страницу для руководителя. База «до» та же, что у таблицы
«Эффект изменений»: выбранный файл сравнения или `baseline` сессии.

Числа листа целиком идут через `src/domain/plan-comparison.ts` (`buildPlanComparison`,
расширен по ревью !319, D-327): площадь/занято/свободно/объектов/ошибок/предупреждений
«было → стало», изменения по названиям (`changes`), находки `validatePlan`, которых не
стало или которые появились (`issueDeltas`, сопоставление по `code`+`refs`), и числа
правил `data/catalog/rules.json` «было → стало» для правил, задетых находками
(`ruleEffects`) — количество через `countInZoneScope` (`domain/inventory`), расстояние до
входа через `openingCentre`+`segmentLength` (`domain/geometry`) без порога, ровно те
примитивы, которыми уже считает сама проверка (`domain/validation`); у каждой строки
правила — свой источник (`sourceNote`), не общая пометка «решение команды»: часть правил
пришла из материалов организаторов. `approval-sheet.ts` (в этом модуле) — тонкая
сборка вокруг `buildPlanComparison`: добавляет только картинки «до»/«после»
(`persistence/plan-svg.renderPlanSvg`, инлайн-SVG без XML-пролога, все слои
принудительно видимы — лист не должен скрывать то, что скрыто у автора листа сейчас) и
допущения/ограничения `comparePlans` из `domain/advice` (тот же детерминированный
сценарий `compare`, без LLM). Штамп — план/отделение, источник «до», дата, поле «автор»
(вводит пользователь, по умолчанию пусто).

`ApprovalSheet.tsx` рендерится через `createPortal(..., document.body)` (D-328): нужен,
чтобы печать могла спрятать всё остальное одним `body > *:not(.approval-sheet) { display:
none }`, не пытаясь через CSS пересилить инлайновый пиксельный размер холста редактора
(`ResizeObserver`, `src/features/editor`) — специфичность стилей с инлайн-атрибутом не
воюет. На экране `position: fixed` кладёт диалог поверх всего независимо от места в DOM,
так что портал ничего не меняет в видимом поведении. Печать — `window.print()`;
PDF получают через «Сохранить как PDF» браузера, отдельная PDF-библиотека не добавлена.
Своя копия фокус-ловушки `file-dialog`/`HotkeysMapDialog`: feature не импортирует
соседнюю feature (`docs/project-structure.md`).
