# CLAUDE.md — правила проекта

Пиши на ~80% ASD-STE100: короткие предложения, одно действие — одно предложение,
один термин — одно значение. Так же пиши отчёты и описания MR.

## Задача

Хакатон Почтатеха «Цифровой двойник отделения Почты России»: 2D-редактор плана ОПС,
модель оборудования, инвентаризация, проверка плана, ИИ-ассистент, 3D-вид.
Пользователь — внутренний заказчик: руководитель отделения, проектировщик
перепланировки, специалист по инвентаризации. Не клиенты отделения (D-057).

- Условия — `task.md`. Пример плана — `example_plan.json`. Библиотека объектов —
  `Перечень_оборудования_ОПС.pdf`.
- Защита — 8 октября 2026, защищаем выбранный заранее SHA. Новые функции — до защиты
  (D-349). Регламент защиты — `TBD`.
- Сервис: <http://158.160.157.55:8080>. `main` в любой день годится для показа.
- Неизвестный факт пиши как `TBD`, не угадывай.

| Критерий | Вес |

| 2D-редактор: качество, удобство, масштабируемость | 30% |

## Как работаем

1. Возьми задачу: `bash scripts/issues.sh free`, затем `take <N>`. Нет задачи —
   `create`. Без задачи файлы не меняем (D-299).
2. Работай в worktree:
   `git worktree add .claude/worktrees/<N>-<тема> -b worktree-<N>-<тема> origin/main`.
3. Проверь (раздел «Проверка»), закоммить свои пути (`git add <пути>`), запушь ветку
   с MR и `Closes #<N>` (`GIT.md`). Разрешение не спрашивай.

- Не бери задачу в `area:`, где работает другой. Задачу без движения 2 ч можно
  перехватить и продолжить её ветку (D-313).
- Риск показа или сдачи — сразу задача с меткой `blocker`.
- `main` всегда зелёный. Сломал — чини раньше своей задачи.
- Модули связаны только через `src/contracts/` и `index.ts`. Контракт меняй отдельным
  MR со списком потребителей.
- Владельцы: tooling и lockfile — поток 5, `src/app/` — поток 2, `src/contracts/` —
  поток 1 (`docs/project-structure.md`).
- Запрещены force-push, `rebase`, `--amend`, `git add -A`, push в `main`, трейлеры
  соавторства ИИ.

## Ограничения организаторов

- Данные только синтетические. Реальные планы, ФИО, телефоны не используем.
- LLM — только Qwen, DeepSeek, GigaChat, YandexGPT по API. Провайдер и модель — из
  `.env`. Секреты — только в `.env`.
- Синтетический расчёт (загрузка зон, очереди) показываем как расчёт, не как
  измерение (D-266).
- Комплект сдачи на одном SHA: GitLab с README, адрес сервиса и доступ; один ZIP с
  исходным и изменённым планом, рекомендацией, её эффектом и инструкцией; PDF до
  20 МБ (делает команда).
- README называет объём данных, на котором проверен редактор (число и команда
  замера), известные ограничения, методы ассистента и внешние зависимости.

## Модель данных

- Метры. `position` — центр объекта, `size_m` — [X, Y]. Направление оси Y и поворота
  — одно решение в `docs/decisions.md`. Преобразование «модель ↔ экран» — только в
  `src/domain/geometry`.
- У зоны и объекта — уникальный `id`, тип, атрибуты. Связь объект → зона хранится
  явно и пересчитывается при перемещении.
- План и инвентаризация — одно состояние. 3D строится из плана и своего состояния
  не хранит.
- Справочники — в `data/catalog/*.json`. Новый тип зоны, объекта, слоя или 3D-модели
  добавляется данными, без правки кода.
- Библиотека содержит минимум условий: рабочие места, кассовые окна, терминалы,
  принтеры, стеллажи, места ожидания, камеры, инженерное оборудование.
- Информационные слои — камеры с зоной обзора, тепловая нагрузка, сотрудники (D-059).
- Два входа равноправны: новый план и готовый размеченный план. Проверяющий начнёт
  с готового (D-058).
- Находки проверки видны на плане. Оба демо-плана из ZIP открываются после любой
  правки формата.
- `example_plan.json` — тестовый набор с ошибками: пересечения объектов, стеллажи
  через перегородку x = 7,5, киоск в ~7 м от входа (норма 3 м), вложенные зоны.

## ИИ-ассистент

- Числа считает код. LLM выбирает сценарий и объясняет.
- Три обязательных сценария: место для рабочего места, окна или стеллажа;
  отсутствующее или лишнее оборудование; влияние изменения на свободную площадь и
  инвентаризацию.
- Рекомендация называет `id` зон и объектов, эффект «было → стало» и правила
  комплектования (правило команды, не норматив Почты).
- Код проверяет ответ модели: `id` существуют, числа совпадают с расчётом. Не
  совпало или API недоступен — показываем расчёт с пометкой «без LLM».

## Код

- Стек: TypeScript, React + Vite, react-konva, Zustand, Zod, Three.js, Fastify,
  Vitest, Playwright. Версии — `package.json`.
- Плоский код, без фабрик, реестров и абстракций «на будущее». Правь только зону
  задачи.
- У действия пользователя есть загрузка, результат и ошибка. Ошибка не теряет правки.
- Идентификаторы и комментарии — английские. Интерфейс и документы — русские.

```bash
npm ci                                  # установка; один раз: npx playwright install chromium
npm run dev                             # свой порт — DEV_PORT=5174
npm run lint && npm run build          # build включает tsc, typecheck отдельно не нужен
npx vitest related --run <файлы>        # тесты правки; правишь data/ или demo/ — npm test
DEV_PORT=5174 npx playwright test tests/e2e/round-trip.spec.ts tests/e2e/demo.spec.ts  # smoke
DEV_PORT=5174 npm run test:e2e          # весь e2e — только qa перед вехой
```

## Тесты

- Тестов — минимум. Тест пишем только для доменной логики: геометрия, проверки плана,
  сохранение → загрузка, демо-планы, проверка ответа модели. Один случай на правило.
  Сначала дополни существующий файл, новый не создавай.
- Для UI, стилей и текстов тест не пишем. Мутаций не делаем.
- Ошибка в доменной логике — сначала воспроизводящий тест.
- Конфликт «изменён / удалён» при `git merge origin/main`, где тест удалён в `main`, —
  прими удаление: `git rm <файл>`.

## Проверка

- Перед push: `git fetch --prune && git merge origin/main`, затем lint, build,
  `vitest related`. Smoke e2e — только если правка задевает сохранение, загрузку,
  `src/state/` или демо-планы.
- Один прогон на MR. Пришёл новый merge в `main` после прогона — только
  `npm run build`, тесты заново не гоняем. Весь `npm test` и весь e2e — у `qa`
  перед вехой.
- UI-правка: пройди сценарий в браузере, сделай один снимок «после» (не в git),
  проверь `Tab` и фокус.
- Готово — проверки зелёные и сценарий пройден: открыть → загрузить демо → изменить
  → сохранить → открыть заново. «Работает» пиши только с командой и её выводом.

## Документы

- md-отчёты, планы и спецификации не пишем. Отчёт — в чат, до 3 строк. Описание
  MR — `Closes #<N>` и до 3 строк.
- `HANDOFF.md`, `docs/decisions.md`, `docs/tz-compliance.md` агент не дописывает
  после каждой задачи. Только по задаче, которая это требует.
- `README.md` держим точным (10% оценки). Строка в `docs/decisions.md` — только если
  решение меняет модель, формат, контракт или правила.
- Объясняем человеку самым простым форматом: текст STE → схема mermaid → одноразовый
  HTML через `/explain` (не в git).

## Агенты

Оркестратор (`/orchestrate`) ведёт `builder` → `reviewer` → `integrator`. Роли —
`docs/agents.md`. Правку `.claude/`, контрактов и формата сохранения проверяет
другой человек или свежий `reviewer`.
