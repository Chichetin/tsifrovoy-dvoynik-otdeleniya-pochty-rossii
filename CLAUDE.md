2D-редактором плана ОПС, моделью оборудования и инвентаризацией, проверкой
корректности, ИИ-ассистентом по перепланировке и упрощённым 3D-видом.

**Для кого** (ответ организаторов на QA-сессии 17.09): внутренний заказчик — операционные
руководители Почты России и специалисты «Почтатеха». Не жители и не клиенты отделения.
Роли, под которые проектируем: руководитель отделения, проектировщик перепланировки,

**накладывать информационные слои (камеры, тепло, сотрудники)**». Сложность трека, по
словам организаторов, не в коде, а в том, чтобы встать на место сотрудника в его роли

`docs/tz-compliance.md`.

Календарь: сдача — **22 сентября 2026, 23:59 МСК** (уточнено 19.09). На всё — **6 дней** от 16.09. Команда — **пять сильных

## Как здесь выигрывают

| Критерий | Вес |
|---|---|
| Качество, удобство и масштабируемость 2D-редактора | **30%** |
| Полнота модели объектов, инвентаризации и расширения справочников | 20% |
| Адекватность и объяснимость рекомендаций ИИ-ассистента | 20% |
| Корректность загрузки, проверки, сохранения и повторного открытия планов | 15% |
| Воспроизводимость запуска и качество README.md | 10% |
| Качество упрощённого 3D-представления | 5% |

Выводы из весов:

- Ядро — 2D-редактор и структурированная модель: вместе с сохранением это 65%.
  Ассистент и 3D опираются на ту же модель и без неё ничего не стоят.
- 3D — 5%: условная геометрия из текущего плана, без материалов, текстур и
  освещения. Организаторы подтвердили приоритет: 2D — базовый функционал, 3D
  «приветствуется для демонстрации руководству». Время на 3D сверх «соответствует
  плану» — потерянные баллы редактора.
- README — 10% почти бесплатных баллов: проверяющий должен открыть сервис, загрузить
  демо-проект, изменить и повторно открыть без нашей помощи.
- «Масштабируемость редактора» — проверяется объёмом данных: условия требуют указать,
  на каком объёме редактор проверялся. Меряем, а не заявляем.
- Работа идёт параллельно пятью потоками по плану
  `docs/plans/2026-09-16-parallel-plan.md`, вехи — его календарь. Первым в `main`
  приходит сквозной путь «помещение → зона → объект → сохранить → открыть заново»
  (17.09), затем ширина: библиотека, слои, проверки, ассистент, 3D. Работающий деплой
  и ZIP — к вечеру 21.09; последний день только на проверку сдачи.

## Команда и интеграция

Сила команды — скорость написания кода. Баллы приносит только то, что соединилось в
`main` и проходит сценарий в браузере. Потоки и владельцы каталогов —
`docs/project-structure.md`, пакеты и зависимости — план.

- **Контракты — единственная точка стыковки.** Типы, схемы и fixtures живут в
  `src/contracts/` (владелец — поток 1). Модуль использует соседа только через
  контракты и его публичный `index.ts`, не через внутренние файлы. Границы импортов
  проверяет `npm run lint`.
- **Изменение контракта — отдельный согласованный MR:** тип, схема, fixtures и список
  затронутых потребителей в описании; merge после их подтверждения. Поменять общий тип
  молча под свой модуль нельзя.
- **Начинать на fixtures можно, принимать — только на реальном модуле.** Пакет не
  считается готовым, пока он не подключён и не проверен с настоящими соседями.
- **`main` всегда зелёный и запускается.** Перед push: `git merge origin/main`, затем
  все проверки из раздела «Код и архитектура». Сломанный `main` чинит тот, чей merge
  его сломал, — это приоритетнее своей задачи.
- **Маленькие MR, часто.** MR живёт часы, не дни. Незаконченная функция вливается
  неподключённой (без вызова из `src/app/`), а не копится в ветке.
- **Сквозной e2e растёт вместе с продуктом.** С первого сквозного пути в `tests/e2e/`
  есть сценарий «открыть → изменить → сохранить → открыть заново»; поток, подключивший
  свою часть, добавляет в него шаг через владельца сценария (поток 5). MR, ломающий
  сценарий, не вливается.
- **Точки сборки дважды в день:** свежий `main` у всех, сценарий пройден в браузере,
  расхождения контрактов и блокеры — в `HANDOFF.md`.
- **У общего файла один владелец:** корневой tooling и lockfile — поток 5, `src/app/` —
  поток 2, `src/contracts/` — поток 1. Строки в `HANDOFF.md`, `docs/decisions.md`,
  `docs/tz-compliance.md` каждый добавляет в своём MR; при конфликте сохраняются обе.

## Неподвижные ограничения (из условий и ответов организаторов)

- **Только синтетические данные.** Отделение придумываем сами и рисуем в своём
  редакторе. Реальные планы БТИ нельзя. ФИО, телефоны и табельные номера из
  HTML-примера в свои данные не переносим.
- **LLM — только по API и только доступные в РФ модели: Qwen, DeepSeek, GigaChat,
  YandexGPT** (ответы организаторов 16.09). Claude, OpenAI, Gemini и прочие в решении
  не используются. Ключи и баланс — наши (D-016), провайдер выбирается по цене и
  оплате из РФ и не хардкодится. Интернет при проверке будет.
- Ключи API и другие секреты в репозиторий не попадают никогда: только `.env` (в
  `.gitignore`) и `.env.example` с плейсхолдерами. Проверяет Stop-хук `check-secrets.sh`.
- Мобильная версия не нужна. **Не делаем**: распознавание PDF/DWG/сканов/БТИ,
  подключение видеокамер, анализ очередей и чистоты **по видео**, интеграцию с 1С,
  фотореалистичное 3D, автоматическую перестановку по рекомендации, клиентские
  сценарии (запись, табло очереди для посетителя).
- Запрещён источник, а не представление: показывать загрузку зон и очереди **можно** —
  как информационный слой поверх синтетических атрибутов плана и наших правил расчёта,
  с явной подписью «числа синтетические». Организаторы на QA-сессии прямо назвали это
  ценностью сервиса (D-060). Выдавать такой расчёт за измеренный нельзя.
- Сдача, три части:
  1. ссылка на GitLab с исходниками и `README.md`, адрес работающего сервиса и
     сведения для доступа;
  2. **один ZIP** с исходным и изменённым вариантами своего плана, рекомендацией
     ассистента, описанием её эффекта и инструкцией повторного открытия; **оба плана
     открываются в редакторе** с зонами, оборудованием, идентификаторами и атрибутами;
  3. **PDF-презентация ≤ 20 МБ** — делает команда вручную, агент готовит только
     скриншоты, цифры и факты для неё.
- README и материалы указывают, на каком объёме данных проверялся редактор, и
  известные ограничения. Методы ассистента, внешние зависимости и их ограничения
  описаны в документации.
- Push в `main` закрыт на сервере для всех команд: только ветка + Merge Request
  (`GIT.md`).

## Модель данных

- Единицы — метры, `position` — центр объекта, `size_m` — [по X, по Y] (как в
  `example_plan.json`). **Направление поворота и направление оси Y** (в примере Y вверх
  и поворот «по часовой», на экране Y вниз) фиксируются одним решением в
  `docs/decisions.md` и одним тестом; преобразование «модель ↔ экран» живёт в одном
  месте.
- У каждого объекта и зоны — уникальный `id`, тип, атрибуты; связь объект → зона
  хранится явно и пересчитывается при перемещении. Изменение плана сразу отражается в
  инвентаризации — это одно состояние, а не две копии.
- **Справочники в данных, не в коде**: типы зон, типы объектов (размеры по умолчанию,
  физический/нефизический, атрибуты с типами), правила комплектования. Новый тип
  добавляется правкой справочника без изменения кода — это прямой подпункт критерия 20%.
- Библиотека покрывает минимум из условий: рабочие места, кассовые окна, терминалы,
  принтеры, стеллажи, места ожидания, камеры, инженерное оборудование. Дополнительно —
  позиции из `Перечень_оборудования_ОПС.pdf`.
- **Слой — это ещё и информационное представление**, а не только группа видимости:
  кроме обычных слоёв объектов есть слои камер (объект и его зона обзора), тепловой
  нагрузки зон и сотрудников. Тип слоя и его представление лежат в справочнике: новый
  слой добавляется данными, без правки компонентов (D-059).
- Формат сохранения описан в README. Изменили формат — демо-планы из ZIP по-прежнему
  открываются (тест на загрузку обоих демо-планов).
- **Два входа равноправны**: создать план с нуля и открыть готовый структурированный
  план с уже размеченными зонами и объектами. Проверяющий начнёт со второго, поэтому в
  демонстрации он идёт первым и отлажен не хуже первого (D-058).

## Известные ловушки материалов (проверено 2026-09-16)

- `example_plan.json` — пример, а не выданные данные: его `_comment` («в формате,
  которым команды получают данные») и `extensibility` — остаток старого брифа.
  Приоритет у `task.md`: формат выбираем сами.
- В примере зоны вложены (`z_waiting` и `z_queue` внутри `z_client`), а формат говорит
  «объект принадлежит одной зоне»; сумма площадей зон 96,75 м² при помещении 78 м².
  Модель вложенности (иерархия или слои) — решение в `docs/decisions.md`, площади
  считаются без двойного счёта.
- В примере есть геометрические ошибки — используем его как тестовый набор для
  проверок: пересекаются `eq_cashier_1`/`eq_rack_1`, `eq_cashier_2`/`eq_rack_2`,
  `eq_atm`/`eq_bench_1`; стеллажи `eq_rack_1`, `eq_rack_2` пересекают перегородку
  x = 7,5 и не лежат целиком в своей зоне; `eq_kiosk` в ~7 м от входа при норме из
  перечня оборудования «не более 3 м».
- HTML-пример — экспорт из Illustrator (SVG + карточки по клику), не редактор. Полезен
  как ориентир атрибутов карточки объекта; WFM, аналитика и мониторинг в обязательный
  объём не входят.

## ИИ-ассистент

- **Числа считает код, не модель.** Площади, свободная площадь, поиск места под
  объект, проверка правил комплектования — детерминированные функции с тестами. LLM
  выбирает сценарий, формулирует объяснение и ссылается на результаты расчёта.
- Три обязательных сценария: место для рабочего места / окна / стеллажа; отсутствующее
  или лишнее оборудование; влияние изменения на свободную площадь и инвентаризацию.
- Каждая рекомендация — структура, а не только текст: что изменить, почему, **какие
  `id` зон и объектов** и параметры плана её обосновывают, эффект «было → стало» по
  показателям, **какие допущения и правила комплектования** использованы (с
  пометкой, что это правило команды, а не норматив Почты).
- Ответ модели проверяется кодом перед показом: упомянутые `id` существуют, числа
  совпадают с расчётом. Не совпало — показываем расчёт, а не текст модели.
- API недоступен или вернул мусор — ассистент показывает рекомендации расчёта с
  шаблонным объяснением и явной отметкой «без LLM». Пустой экран — дефект.
- Провайдер и модель — через переменные окружения (`.env`), без хардкода; названия
  моделей и адреса API берём из актуальной документации провайдера, не из памяти.

## 3D

- Строится автоматически из текущего 2D-состояния, своего состояния не хранит:
  изменили план — 3D соответствует. Условные объёмы (коробки по `size_m` и высоте из
  справочника), зоны — цветом пола.

## Код и архитектура

- Стек (D-009): TypeScript 6.0, React 19 + Vite 8, react-konva/Konva — 2D, Zustand —
  состояние, Zod 4 — схемы, Three.js — 3D, Fastify 5 — сервер, Vitest 5 + Testing
  Library, Playwright, ESLint 10. Точные версии — `package.json`, Node ≥ 22.12. Новая
  зависимость — через владельца корневого tooling (поток 5), lockfile в чужих MR не правится.
- Команды:

  ```bash
  npm ci                              # установка строго по lockfile
  npx playwright install chromium     # один раз на машину: браузер для e2e
  npm run dev                         # http://127.0.0.1:5173 (свой порт — например DEV_PORT=5174)
  npm test                            # unit-тесты (Vitest)
  npm run test:e2e                    # браузерные тесты (Playwright сам поднимает dev)
  DEV_PORT=5174 npm run test:e2e      # из worktree: свой порт, чужой сервер не берётся
  npm run typecheck && npm run lint && npm run build
  ```

- Стенд UI-пакета до подключения в приложение: `tests/harness/<ID>.tsx` с default
  export компонента → `npm run dev` → `http://127.0.0.1:5173/tests/harness/?id=<ID>`
  (порт — из `DEV_PORT`, по умолчанию 5173).
  В production-сборку стенды не попадают.
- Границы импортов из `docs/project-structure.md` проверяет `npm run lint`
  (`no-restricted-imports` в `eslint.config.js`): domain без React и UI-библиотек,
  features не импортируют соседние features, app, state и server, и т. д.
- Плоский код: небольшие модули, явные типизированные контракты, никаких фабрик,
  реестров, DI-контейнеров и конфиг-движков «на будущее». Библиотеки — идиоматично и
  на полную; свои «платформы» поверх них — нет.
- Геометрия (площадь полигона, принадлежность, пересечение повёрнутых
  прямоугольников) — чистые функции без UI, покрытые тестами.
- Конфигурация — только через переменные окружения; дефолты без секретов.
- Каждое действие пользователя имеет состояния загрузки, результата и ошибки. Ошибка
  сохранения, загрузки или API не превращается молча в успех и не теряет правки.
- Идентификаторы и комментарии в коде — английские; интерфейс и документация — русские.
- Правки только в зоне задачи: не переформатировать и не рефакторить соседний код.

## Тесты и доказательство результата

- Новая логика → тест в том же коммите. Багфикс начинается с воспроизводящего теста.
- Обязательные тесты: геометрия и площади; все проверки корректности на
  `example_plan.json` (ловушки выше); round-trip «сохранить → загрузить → то же
  состояние» (геометрия, зоны, оборудование, `id`, атрибуты, связи); загрузка обоих
  демо-планов; валидация ответа ассистента.
- «Должно работать» не существует. Готово — это: тесты зелёные и сценарий пройден в
  браузере (открыть → загрузить демо → изменить → сохранить → открыть заново),
  результат записан.
- Объём, на котором проверялся редактор (число объектов, зон, время отклика), —
  измеренные числа с командой замера, не оценка.
- Stop-хук `check-tests.sh` сам находит `npm test` / `pytest` и не даёт закончить ход с
  красными тестами; пока тестов нет, он молчит. Сценарий в браузере хук не проверяет.
- Ни одно «проверено» / «работает» в чате, README или отчёте не пишется без команды и
  её вывода.

## Принципы Карпаты — адаптация под задачу

1. **Become one with the domain.** Прочитать перечень оборудования и пример плана до
   модели данных; нарисовать условное отделение на бумаге до кода.
2. **Overfit a single scenario first.** Одна зона и один объект проходят весь путь
   «добавить → сохранить → открыть», потом ширина библиотеки.
3. **Тупой бейзлайн прежде умного.** Правила и расчёт раньше LLM; прямоугольники
   раньше красивых иконок.
4. **Визуализировать всё.** Ошибки проверки подсвечиваются на плане, а не только
   списком.
5. **Воспроизводимость.** Одна команда запуска, зафиксированные версии, демо-данные в
   репозитории.
6. **LLM fail silently.** Модель уверенно врёт про площади и `id` — сверяем с расчётом.
7. **Журнал решений.** Решение — строка в `docs/decisions.md`: что выбрали, почему,
   что отвергли. Это материал для README и презентации.

## Работа с Claude Code

- Система агентов — `docs/agents.md`. Главная сессия в основной копии — оркестратор
  (скилл `orchestrate`, команда `/orchestrate`): код не пишет, заводит worktree и
  ведёт конвейер `builder` → `reviewer` (только diff) → `integrator` (один за раз) →
  `qa` (сценарий в браузере). Вне конвейера: `operator` проходит приложение в роли
  сотрудника, `scribe` пишет README и доску, `jury` оценивает.
- Субагент `jury` (`.claude/agents/jury.md`) оценивает текущее состояние по критериям
  как проверяющий: видит только артефакты. Запускать перед каждой вехой и перед сдачей.
- Скилл `submission-checklist` — проверка комплекта сдачи. Скиллы запускать явно: сами
  они вызываются редко.
- `docs/tz-compliance.md` — матрица «пункт условий → артефакт → проверка → статус»;
  строку обновлять в том же коммите, что и артефакт.
- SessionStart-хук `session-context.sh` показывает ветку, worktree и активные задачи
  `HANDOFF.md`. SubagentStop-хук `check-worktrees.sh` ищет секреты во всех worktree,
  где работали субагенты. Хуки проверяются `bash .claude/hooks/test-hooks.sh`.
- Хук `check-upstream.sh` сам делает `git fetch`: если в `origin/main` появились чужие
  коммиты в твоих файлах или в общих правилах и доске, он их показывает. Оценить, не
  противоречат ли они задаче; противоречат — остановиться и спросить человека.
- Раз в несколько коммитов пересказать правила этого файла своими словами. Если
  правило пропущено, раздел пора сократить или вынести в скилл, а не выделять жирнее.

## Ревью

- Крупное или рискованное (формат сохранения, модель данных, `.claude/`) — MR с
  ревью другим участником или свежим субагентом, который видит только diff.
- Чек-лист: нет секретов; тест есть; сценарий «открыть → изменить → сохранить →
  открыть» не сломан; демо-планы открываются; состояния ошибок есть; зависимости
  зафиксированы; решение записано.

## Git

Кратко (полностью — `GIT.md`): задача, меняющая файлы, делается **в своём worktree**
(`claude -w <поток>-<тема>` → `.claude/worktrees/…`, ветка `worktree-…`). Push в
`main` закрыт на сервере: ветка пушится с созданием **Merge Request** в `main`, merge —
в GitLab. Коммит и push ветки — **автоматически, без запроса разрешения** после
каждого законченного и проверенного шага; в коммит только свои файлы через
`git add <пути>`; перед работой и перед push — `git fetch --prune && git status -sb`;
force-push запрещён; трейлеры соавторства ИИ в коммиты и MR не добавляем.
