# CLAUDE.md — правила проекта

Правила написаны на ~80% ASD-STE100: одно предложение — одно действие. Отчёты,
описания MR и ответы пиши так же (раздел «Как писать»).

## Задача

Хакатон Почтатеха, задача «Цифровой двойник отделения Почты России». Мы делаем
веб-сервис: 2D-редактор плана ОПС, модель оборудования, инвентаризацию, проверку
плана, ИИ-ассистента по перепланировке и 3D-вид.

Пользователь — внутренний заказчик: операционные руководители Почты России и
специалисты «Почтатеха». Клиенты отделения — не пользователь. Роли:

- руководитель отделения;
- проектировщик перепланировки;
- специалист по инвентаризации и эксплуатации.

Цель трека по словам организаторов: «масштабируемый веб-редактор: конструировать
планы, расставлять мебель и оборудование, накладывать информационные слои (камеры,
тепло, сотрудники)». Сложность трека — встать на место сотрудника в его роли (D-057,
D-059).

Источники:

- условия — `task.md`;
- пример структуры плана — `example_plan.json`;
- ориентир для библиотеки объектов — `Перечень_оборудования_ОПС.pdf`;
- визуальный ориентир — `ОПС_115534_демо_плана.html` (21 МБ, не в git, скачать со
  страницы хакатона);
- Git — `GIT.md`; задачи — GitLab Issues (`bash scripts/issues.sh`); решения —
  `docs/decisions.md`; вопросы организаторам — `HANDOFF.md`.

## Критерии

| Критерий | Вес |
|---|---|
| Качество, удобство и масштабируемость 2D-редактора | **30%** |
| Полнота модели объектов, инвентаризации и расширения справочников | 20% |
| Адекватность и объяснимость рекомендаций ИИ-ассистента | 20% |
| Корректность загрузки, проверки, сохранения и повторного открытия планов | 15% |
| Воспроизводимость запуска и качество README.md | 10% |
| Качество упрощённого 3D-представления | 5% |

- 2D-редактор, модель и сохранение — 65%. Ассистент и 3D работают на той же модели.
- 3D весит 5%, но его запоминают на защите. Цель — узнаваемые модели со светом и
  материалами (#59).
- README — 10%. Проверяющий без нашей помощи открывает сервис, загружает демо,
  меняет план и открывает его заново.
- Масштабируемость измеряем. Число объектов и зон, время отклика и команда замера —
  в README.
- Порядок работ: дефекты и достоверность ассистента → законченные сценарии ролей →
  выпуск и комплект защиты. Дорожная карта —
  `docs/superpowers/plans/2026-09-28-defense-roadmap.md`. Очередь — GitLab Issues.

## Как работаем

1. Возьми задачу: `bash scripts/issues.sh free`, затем `take <N>`. Подходящей задачи
   нет — создай её (`create`, шаблон `.gitlab/issue_templates/Задача.md`). Правило
   действует и для одной строки (D-299).
2. Открой worktree:
   `git worktree add .claude/worktrees/<N>-<тема> -b worktree-<N>-<тема> origin/main`.
   Правь файлы только в нём.
3. Сделай работу и проверь её (раздел «Проверка»).
4. Закоммить свои пути и запушь ветку с MR (`GIT.md`). Разрешение на коммит и push
   не спрашивай.
5. В описании MR напиши `Closes #<N>`. Merge делают в GitLab.

Правила 1–2 держат хуки: `check-issue.sh` для Claude Code, `.githooks/pre-commit` и
`pre-push` для Codex и людей, `scripts/gitlab-mr.sh merge` для MR. Проверь себя:
`bash scripts/issues.sh check`.

Очередь:

- У задачи есть `area:` (`model`, `editor`, `panels`, `assistant`, `release`),
  приоритет `P0`–`P2`, строка «Зависит от #…» и оценка модели.
- Не бери задачу в `area:`, где работает другой человек. `take` откажет сам.
- Задачу без движения больше 2 ч можно перехватить (D-313). Продолжай её ветку. Не
  переписывай чужие коммиты.
- Риск показа или сдачи не закрыт в этом ходе — сразу создай задачу с меткой
  `blocker`.

Интеграция:

- `main` всегда зелёный и запускается. Сломал `main` — чини его раньше своей задачи.
- Делай маленькие MR. Незаконченную функцию вливай без вызова из `src/app/`.
- Модули связаны только через `src/contracts/` и публичный `index.ts`. Границы
  импортов проверяет `npm run lint`.
- Контракт меняй отдельным MR: тип, схема, fixtures и список потребителей. Merge —
  после согласия потребителей.
- На fixtures можно начать. Принимаем только на реальном модуле.
- Владельцы: tooling и lockfile — поток 5, `src/app/` — поток 2, `src/contracts/` —
  поток 1. Карта каталогов — `docs/project-structure.md`.

## Ограничения из условий и ответов организаторов

- Данные только синтетические. Отделение придумываем сами. Реальные планы БТИ, ФИО,
  телефоны и табельные номера не используем.
- LLM — только по API и только Qwen, DeepSeek, GigaChat, YandexGPT. Claude, OpenAI,
  Gemini и другие в решении не используем. Провайдер и модель берём из `.env`, не из
  кода (D-016).
- Секреты — только в `.env`. В `.env.example` — плейсхолдеры. Хук `check-secrets.sh`
  это проверяет.
- Синтетический расчёт не выдаём за измерение. Слои загрузки и очереди показывать
  можно: это расчёт по синтетическим атрибутам плана. README и презентация это
  раскрывают (D-060, D-266).
- Условиями не требуются, но не запрещены (D-349): мобильная версия, распознавание
  PDF, DWG и сканов (только синтетических), видеокамеры, анализ видео, 1С,
  фотореалистичное 3D, автоматическая перестановка, клиентские сценарии. Пользователь
  остаётся внутренним заказчиком (D-057).
- Push в `main` закрыт на сервере. Только ветка и MR.
- Комплект сдачи согласован с одним SHA. Можно ли его заменить на финале — `TBD`.
  1. GitLab с `README.md`, адрес сервиса и доступ.
  2. Один ZIP: исходный и изменённый план, рекомендация ассистента, её эффект,
     инструкция повторного открытия. Оба плана открываются в редакторе с зонами,
     объектами, `id` и атрибутами.
  3. PDF-презентация до 20 МБ. Её делает команда. Агент готовит только снимки, числа
     и факты.
- README называет объём данных, на котором проверен редактор, и известные
  ограничения. Документация описывает методы ассистента и внешние зависимости.

## Модель данных

- Единицы — метры. `position` — центр объекта. `size_m` — [по X, по Y], как в
  `example_plan.json`.
- Направление оси Y и поворота — одно решение в `docs/decisions.md` и один тест.
  Преобразование «модель ↔ экран» живёт в одном месте (`src/domain/geometry`).
- У зоны и объекта есть уникальный `id`, тип и атрибуты. Связь объект → зона
  хранится явно и пересчитывается при перемещении.
- План и инвентаризация — одно состояние, не две копии.
- Справочники — в данных (`data/catalog/*.json`), не в коде: типы зон, типы объектов
  (размеры, физический или нет, атрибуты с типами), правила комплектования, типы
  слоёв. Новый тип добавляется правкой справочника без правки кода (критерий 20%).
- Библиотека содержит минимум из условий: рабочие места, кассовые окна, терминалы,
  принтеры, стеллажи, места ожидания, камеры, инженерное оборудование. Дополнительно —
  позиции из перечня оборудования.
- Слой — это группа видимости или информационное представление: камеры с зоной
  обзора, тепловая нагрузка зон, сотрудники. Новый слой добавляется данными (D-059).
- Находки проверки видны на плане, а не только списком.
- Формат сохранения описан в README. Формат изменился — оба демо-плана из ZIP
  по-прежнему открываются.
- Два входа равноправны: новый план с нуля и готовый размеченный план. Проверяющий
  начнёт с готового плана, поэтому он идёт в демонстрации первым (D-058).

## Ловушки `example_plan.json`

- Это пример, а не выданные данные. Его `_comment` и `extensibility` — остаток
  старого брифа. Приоритет у `task.md`: формат выбираем сами.
- Зоны вложены: `z_waiting` и `z_queue` лежат внутри `z_client`. Сумма площадей зон —
  96,75 м², помещение — 78 м². Площади считаем без двойного счёта.
- Геометрические ошибки примера — наш тестовый набор:
  - пересекаются `eq_cashier_1`/`eq_rack_1`, `eq_cashier_2`/`eq_rack_2`,
    `eq_atm`/`eq_bench_1`;
  - `eq_rack_1` и `eq_rack_2` пересекают перегородку x = 7,5 и выходят из своей зоны;
  - `eq_kiosk` стоит в ~7 м от входа, норма из перечня — не более 3 м.
- HTML-пример — экспорт из Illustrator, не редактор. Он полезен как ориентир
  атрибутов карточки объекта.

## ИИ-ассистент

- Числа считает код. Площади, свободную площадь, место под объект и правила
  комплектования считают детерминированные функции с тестами. LLM выбирает сценарий
  и объясняет результат расчёта.
- Обязательные сценарии:
  1. место для рабочего места, окна или стеллажа;
  2. отсутствующее или лишнее оборудование;
  3. влияние изменения на свободную площадь и инвентаризацию.
- Рекомендация — структура, а не только текст: что изменить, почему, какие `id` зон и
  объектов это обосновывают, эффект «было → стало», допущения и правила
  комплектования. Правило помечено как правило команды, не норматив Почты.
- Код проверяет ответ модели перед показом: `id` существуют, числа совпадают с
  расчётом. Не совпало — показываем расчёт.
- API недоступен или ответ негодный — показываем расчёт с шаблонным объяснением и
  пометкой «без LLM». Пустой экран — дефект.
- Имена моделей и адреса API бери из актуальной документации провайдера, не из
  памяти.

## 3D

- 3D строится из текущего 2D-состояния и своего состояния не хранит.
- Зоны — цветом пола. Объект — узнаваемая модель своего типа по `size_m` и высоте из
  справочника, со светом и материалами (#59).
- Модель типа — поле справочника (архетип), не `switch` по типу в коде. Тип без
  модели — коробка, поэтому новый тип 3D не ломает.

## Тесты

Тест стоит времени дважды: на написание и на каждый прогон. Пиши мало. Пиши только
там, где ошибку не видно глазами.

Тест нужен только для доменной логики:

- геометрия и площади;
- проверки плана на `example_plan.json` (ловушки выше);
- сохранение → загрузка → то же состояние: геометрия, зоны, объекты, `id`, атрибуты,
  связи;
- загрузка обоих демо-планов;
- расчёты ассистента и проверка ответа модели.

Тест не нужен:

- для компонентов, раскладки, стилей, текстов и иконок;
- для поведения, которое уже покрыто;
- для второго и третьего случая того же правила. Один случай на правило.

Ещё:

- Ошибка в доменной логике — сначала воспроизводящий тест, потом исправление.
- Мутационную проверку не делаем.
- Новый e2e-spec пиши, только если задача его требует. Сквозной сценарий —
  `tests/e2e/round-trip.spec.ts` (владелец — поток 5).
- Хук `check-tests.sh` в конце хода запускает `npm test`, если файлы менялись.
  Красные тесты не дают закончить ход.

## Проверка

Готово — это проверки зелёные и сценарий в браузере пройден: открыть → загрузить
демо → изменить → сохранить → открыть заново.

Перед push (builder):

1. `npm run typecheck && npm run lint && npm run build`.
2. `npx vitest related --run <изменённые файлы>`.
3. Smoke e2e (команда выше). Весь e2e не запускай.

Перед merge (integrator, один раз на MR): `npm test` и весь `npm run test:e2e`.

UI-правка — дополнительно:

1. Пройди сценарий в браузере на dev-стенде.
2. Сделай один снимок «после» (Playwright, `clip`). Снимок положи в scratchpad, не в
   git.
3. Проверь клавиатуру: `Tab` доходит до нового элемента, фокус виден, у кнопки есть
   имя.

Скиллы `ui-ux-pro-max`, `frontend-design`, `accessibility-*` и `playwright-*` — по
желанию, не обязательно.

Не пиши «работает» или «проверено» без команды и её результата.

## Документы

Агент пишет код, а не отчёты о коде. md-файл попадает в git, только если его
прочитает проверяющий или команда через неделю.

Пиши:

- `README.md` — 10% оценки. Держи его точным. Замеры масштаба — число и команда прямо
  в README.
- `docs/decisions.md` — одна строка, только если решение меняет модель, формат,
  контракт или правила. До трёх предложений: что выбрали, почему, что отвергли.
- `HANDOFF.md` — вопросы организаторам и их ответы. Итог дня — одна запись в день.
- README модуля — только если изменилась граница модуля или его файлы.
- `docs/tz-compliance.md` — обновляет `scribe` перед выпуском, а не каждый MR.

Не пиши:

- отчёты о прогонах и проверках. `docs/verification/` — архив, его не пополняем;
- планы и спецификации задачи в `docs/plans/` и `docs/superpowers/`. План живёт в
  задаче GitLab или в чате;
- пересказ diff в md-файлах.

Описание MR — по шаблону `.gitlab/merge_request_templates/Default.md`, до 15 строк.

## Как писать

Пиши на ~80% ASD-STE100. Это контролируемый язык техдокументации для обслуживания
авиатехники. Такой текст читается быстрее.

- Одно предложение — одна мысль. Инструкция — до 20 слов, описание — до 25 слов.
- Инструкция — в повелительном наклонении: «Запусти», «Не меняй».
- Действительный залог: кто делает что.
- Один термин — одно значение (словарь ниже). Не заменяй термин синонимом.
- Три шага и больше — нумерованный список.
- Без вводных слов, оценок и итоговых фраз: «важно отметить», «таким образом»,
  «ключевой».
- Число, `id` и путь — точно. Результат проверки — команда и её вывод.

| Термин | Значение | Не пиши |
|---|---|---|
| план | документ ОПС: помещение, зоны, объекты, слои | схема, чертёж, макет |
| помещение | внешний контур плана со стенами и проёмами | комната, здание |
| зона | область плана с типом | участок, регион |
| объект | экземпляр оборудования или мебели на плане | элемент, сущность, нода |
| тип | запись справочника для объекта, зоны или слоя | класс, категория |
| справочник | данные типов в `data/catalog/` | конфиг, реестр |
| слой | группа видимости или информационное представление | оверлей |
| находка | результат проверки плана | ошибка, варнинг |
| задача | GitLab Issue #N | тикет, карточка, пакет |

## Как объяснять результат человеку

Агенты делают всё больше работы сами. Человек всё больше проверяет и понимает. Помоги
ему понять быстро (A. Karpathy). Выбери самый простой формат, которого достаточно:

1. Текст на ~80% STE — по умолчанию: ответ в чате, описание MR.

## Агенты и хуки

- Оркестратор — главная сессия в основной копии (скилл `/orchestrate`). Код он не
  пишет. Он ведёт конвейер `builder` → `reviewer` → `integrator` (один за раз).
  Роли — `docs/agents.md` и `.claude/agents/*.md`.
- Вне конвейера: `qa` проверяет `main` и деплой, `operator` проходит приложение в роли
  сотрудника, `scribe` пишет README, `jury` оценивает по критериям. `jury` и скилл
  `submission-checklist` запускай перед вехой и сдачей.
- Хуки (проверка — `bash .claude/hooks/test-hooks.sh`):
  - `session-context.sh` на старте — ветка, `blocker`, мои задачи, занятые `area:`;
  - `check-issue.sh` перед правкой — правка, commit и push только в worktree взятой
    задачи;
  - `check-secrets.sh` и `check-tests.sh` в конце хода — секреты и красные тесты;
  - `check-upstream.sh` — чужие коммиты в `origin/main` по твоим файлам. Коммит
    противоречит задаче — остановись и спроси человека;
  - `check-worktrees.sh` после субагента — секреты во всех worktree.

## Ревью

- Формат сохранения, модель данных, контракты и `.claude/` — ревью другим человеком
  или свежим `reviewer`, который видит только diff.
- Чек-лист: нет секретов; у доменной логики есть тест; сценарий «открыть → изменить →
  сохранить → открыть» цел; демо-планы открываются; есть состояния ошибок; решение
  записано, если оно меняет модель, формат или правила.

## Git

Полностью — `GIT.md`.

- Одна задача — один worktree `.claude/worktrees/<N>-<тема>` — ветка
  `worktree-<N>-<тема>` — один MR с `Closes #<N>`.
- Перед работой и перед push: `git fetch --prune && git status -sb`, затем
  `git merge origin/main`.
- В коммит — только свои файлы: `git add <пути>`.
- Не используй force-push, `rebase`, `--amend` и `git add -A`.
- Трейлеры соавторства ИИ в коммиты и MR не добавляем.
