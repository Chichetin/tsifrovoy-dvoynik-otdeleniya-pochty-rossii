## P1. Площадка для публичного адреса

```text
Ты — независимый инженер по развёртыванию. Нужен ответ для решения, которое
принимается сегодня, а не обзор рынка. Сегодня 20.09.2026; адрес нужен к 22.09.2026,
23:59 МСК и должен работать как минимум до 30.09.2026 (дата проверки жюри неизвестна).

Задача: поднять публичный адрес для небольшого веб-сервиса и держать его до конца
сентября. Сервис — один Docker-контейнер на базе node:22-alpine, многоступенчатая
сборка, внутри один процесс Node, который отдаёт и статику одностраничного
приложения, и HTTP API. Запускается командой docker compose up --build -d, слушает
порт 8080 (меняется переменной PORT). Базы данных нет, диск между перезапусками не
нужен: пользователь хранит данные в файлах у себя. Есть проверка живости
GET /api/health. Один секрет — API-ключ языковой модели — задаётся переменной
окружения и не должен попадать ни в образ, ни в репозиторий. Сервису нужны исходящие
HTTPS-запросы к API языковой модели (Yandex Cloud AI Studio и DeepSeek); ответ модели
приходит за 20–60 секунд, поэтому обратный прокси или балансировщик площадки не
должен рвать соединение раньше 60 секунд.

Требования к площадке:
- публичный HTTPS-адрес, открывается в браузере без регистрации, логина и VPN;
  выданный поддомен подходит, свой домен не нужен;
- оплата из России картой российского банка либо тариф, на котором оплата не нужна;
- развёртывание человеком за час без прежнего опыта именно с этой площадкой;
- переменные окружения задаются без пересборки образа;
- сервис отвечает сразу, когда его откроют: если тариф усыпляет контейнер, назови
  время холодного старта;
- исходящие запросы к внешним API не блокируются — отдельно проверь, доступны ли
  названные API языковых моделей с IP-адресов этой площадки и её региона.

Сравни 5–7 реальных вариантов: российские облака и хостинги, зарубежные PaaS с
поддержкой Docker, обычный VPS с установкой Docker руками. Для каждого дай тариф и
цену в рублях в месяц с датой проверки, способ оплаты из РФ, поддержку Docker и
compose, способ задать секреты, наличие HTTPS из коробки, лимиты (трафик, память,
время работы, срок действия бесплатного тарифа), поведение при превышении лимита,
холодный старт и то, что произойдёт с адресом через месяц.

Правила: цену, возможность оплаты из РФ и лимиты подтверждай ссылкой на официальную
страницу с датой проверки; не пересказывай статьи и подборки; то, что нельзя узнать
без регистрации, помечай UNKNOWN. Не предлагай Kubernetes, CI/CD, terraform,
мониторинг и балансировку — нужен один контейнер на одном хосте.

Формат ответа:
1. Таблица: площадка → цена → оплата из РФ → Docker/compose → секреты → HTTPS →
   лимиты → холодный старт → источник с датой.
2. Рекомендация: основной вариант и запасной, с критерием переключения.
3. Пошаговая инструкция для основного варианта — от регистрации до открытого
   HTTPS-адреса, с командами.
4. Что проверить сразу после подъёма, включая запрос к API модели с ответом дольше
   30 секунд и открытие адреса с чужой машины.
5. Риски: что может отвалиться за два дня и что тогда делать.
6. Источники с датами проверки, UNKNOWN и допущения.
```

## P2. Показ и презентация

```text
Ты — независимый исследователь конкурсных демонстраций инженерных веб-продуктов.
Нужен порядок показа готового продукта, а не советы по его доработке: код заморожен,
до сдачи двое суток (сдача 22.09.2026, 23:59 МСК).

Продукт — веб-сервис «Цифровой двойник отделения Почты России» для внутреннего
заказчика: руководителя отделения, проектировщика перепланировки, специалиста по
инвентаризации и эксплуатации. Данные синтетические, реальные планы БТИ и
персональные данные запрещены условиями.

Критерии жюри и веса: качество и масштабируемость 2D-редактора — 30%; полнота модели
объектов, инвентаризации и расширяемость справочников — 20%; адекватность и
объяснимость рекомендаций ассистента — 20%; корректность загрузки, проверки,
сохранения и повторного открытия планов — 15%; воспроизводимость запуска и качество
README — 10%; упрощённое 3D — 5%.

Что в продукте уже есть и что можно показать:
- 2D-редактор: контур помещения, перегородки, проёмы, вложенные зоны, объекты 25
  типов из справочника; перенос, поворот, изменение размера, удаление, выделение
  рамкой и групповая правка, отмена и повтор, копирование; привязка к сетке 0,5 м и
  к граням соседних объектов и стен с отключением клавишей Alt; масштабирование к
  курсору, «вписать план», паспорт объекта при наведении, выгрузка плана картинкой.
- Слои: обычные слои видимости и информационные — камеры с сектором обзора, тепловая
  нагрузка зон, сотрудники, очередь; у каждого легенда и подпись «числа синтетические».
- Справочники в данных: типы объектов, зон, слоёв и правила комплектования лежат в
  JSON и правятся панелью «Справочник» прямо в редакторе, новый тип не требует правки
  кода; снимок справочника сохраняется внутри файла плана.
- Инвентаризация: перечень объектов с инвентарными номерами, сортировка, разрез по
  зонам, выгрузка CSV, таблица площадей. Считается из того же документа, что и план.
- Проверки корректности: пересечения объектов, выход за границы помещения и зоны,
  стеллаж поперёк перегородки, терминал дальше трёх метров от входа. Находки
  помечаются маркерами на плане, по клику редактор переходит к объекту.
- Ассистент: три сценария — найти место для рабочего места, кассового окна или
  стеллажа; показать недостающее и лишнее оборудование по правилам комплектования;
  показать эффект изменения «было → стало» по площадям и инвентаризации. Числа
  считает код, языковая модель выбирает формулировку и обязана сослаться на
  существующие идентификаторы и факты, ответ проверяется кодом перед показом. Без
  ключа провайдера ассистент работает и честно помечает режим «Без LLM».
- 3D: условные объёмы, строятся из того же документа, своего состояния не хранят.
- Сохранение: план сохраняется в JSON и открывается заново без потерь; в браузере
  ведётся черновик; открываются оба демонстрационных плана.
- Комплект сдачи: ZIP с исходным и изменённым вариантами плана, рекомендацией
  ассистента и инструкцией повторного открытия; презентация в PDF до 20 МБ делается
  человеком вручную.

Проверяющий должен сам открыть сервис по ссылке, загрузить демонстрационный план,
изменить его, сохранить и открыть снова — без помощи команды.

Спроектируй показ. Отдельно учти, что демонстрация и презентация — разные носители:
живой показ идёт в браузере, а PDF читают без нас.

Правила: не придумывай функции, которых нет в списке выше; не предлагай анимации и
оформление вместо доказательств; каждое утверждение, которое попадёт на слайд,
сопровождай пометкой, чем его подтверждать — числом, файлом, тестом или показом на
экране. Не выдумывай адрес сервиса, отзывы жюри и результаты замеров.

Формат ответа:
1. Таймлайн живого показа 0:00–5:00: действие, что видно на экране, чем
   подтверждается, сколько занимает.
2. Раскладка PDF по слайдам под веса 30/20/20/15/10/5: слайд → тезис → кадр или
   число на нём → чем подтверждается.
3. План Б: недоступна языковая модель, не работает WebGL, недоступен публичный адрес.
4. Пять способов потерять баллы на показе и дешёвая проверка против каждого.
5. Что показать первым в первые 60 секунд и почему — с точки зрения роли зрителя.
6. Допущения и то, чего по описанию продукта понять нельзя.
```

## P3. Запасной провайдер LLM

Запускать только если решим страховать основной ключ. Сейчас ассистент работает на
DeepSeek-V4-Flash через Yandex Cloud AI Studio, протокол OpenAI-совместимый, адрес,
модель и ключ берутся из окружения.

```text
Ты — независимый исследователь доступности LLM API в России. Нужен инженерный ответ,
а не обзор моделей. Сегодня 20.09.2026.

Контекст: у небольшого веб-сервиса ассистент обращается к языковой модели по
OpenAI-совместимому протоколу chat completions — адрес метода, идентификатор модели и
ключ задаются переменными окружения, в коде их нет. Сейчас работает DeepSeek-V4-Flash
через Yandex Cloud AI Studio. Нужен запасной провайдер на случай, если ключ или баланс
подведут в день сдачи. По условиям конкурса допустимы только Qwen, DeepSeek, GigaChat
и YandexGPT.

Исследуй GigaChat и YandexGPT как запасные варианты и ответь по официальной
документации провайдеров:
- точный адрес метода chat completions и идентификатор модели;
- есть ли OpenAI-совместимый режим — то есть можно ли переключиться сменой двух
  переменных окружения, или нужен отдельный адаптер в коде;
- авторизация: что именно служит ключом, как он получается и сколько времени это
  занимает; для GigaChat отдельно — нужны ли сертификаты НУЦ Минцифры, и если да, то
  что придётся положить в Docker-образ на node:22-alpine;
- поддержка структурированного ответа: можно ли потребовать строгий JSON заданной
  формы;
- лимиты: размер ответа, таймауты, ограничение частоты запросов;
- тарификация, валюта, способ оплаты и возможность регистрации физическим лицом из РФ;
- регион размещения и доступность API с российского и зарубежного IP-адреса.

Отдели документацию от утверждения «доступно» и от реально выполненного запроса. Если
что-то нельзя узнать без аккаунта или ключа, так и напиши. Не проси меня вводить
секрет и не приводи ключи в ответе.

Формат ответа:
1. Таблица: провайдер → модель → адрес метода → OpenAI-совместимость → строгий JSON →
   авторизация → цена → регион → источник с датой.
2. Какой из двух дешевле подключить как запасной и сколько это займёт в часах.
3. Минимальная проверка связи: команда или псевдокод, без секретов в выводе, с
   логированием только статуса, модели и времени ответа.
4. Матрица отказов: ключ отозван, баланс исчерпан, таймаут, пустой ответ, отказ
   модели — и что делает сервис в каждом случае.
5. Чего нельзя утверждать без аккаунта или живого запроса.
6. Официальные источники с датами проверки и UNKNOWN.
```

## P4. Финальный аудит

Запускать последним, после выбора коммита сдачи: аудит на более раннем состоянии
устареет за ночь. **Прикрепить:** `task.md`, `README.md`, `docs/tz-compliance.md`,
`docs/submission.md`, `HANDOFF.md`, `demo/README.md`, `demo/effect.md`. Секреты, `.env`
и персональные данные не прикладывать.

```text
Ты — независимый строгий рецензент. Тебе приложены условия конкурса и документы
готового проекта «Цифровой двойник отделения Почты России». Сдача — 22.09.2026,
23:59 МСК; код заморожен, время осталось только на проверку и оформление.

У команды есть собственная внутренняя оценка, и повторять её не нужно. Твоя работа —
найти расхождения: места, где документ обещает не то, что подтверждается приложенными
файлами, где утверждение нельзя проверить, где формулировка выдаёт расчёт за измерение
или правило команды за норматив.

Критерии и веса: 2D-редактор и масштабируемость — 30%; модель, инвентаризация и
расширяемость справочников — 20%; рекомендации ассистента — 20%; загрузка, проверки,
сохранение и повторное открытие — 15%; воспроизводимость и README — 10%; 3D — 5%.
Обязательный сценарий проверяющего: открыть сервис, загрузить демонстрационный план,
изменить, сохранить, открыть заново — без помощи команды.

Комплект сдачи состоит из трёх частей: ссылка на репозиторий с README, адрес
работающего сервиса и сведения для доступа; один ZIP с исходным и изменённым
вариантами плана, рекомендацией ассистента, описанием её эффекта и инструкцией
повторного открытия; презентация PDF не более 20 МБ.

Для каждого вывода указывай доказательство — файл и строку из приложенного — либо
пиши UNKNOWN. Отдели то, что видно в документах, от того, что можно подтвердить только
запуском в браузере. Не предлагай изменений, на которые нет времени, и не считай
рекомендацию доказательством.

Формат ответа:
1. Вердикт: готово / условно готово / не готово, с доказательствами.
2. Таблица: критерий → факт → пробел → риск → действие → чем проверить.
3. Расхождения между документами и между документом и заявленным результатом.
4. Пять действий с наибольшей отдачей до сдачи, с ценой в часах и риском.
5. Команды и браузерные сценарии для финальной проверки.
6. Формулировки, которые нельзя оставлять в README и презентации, и чем их заменить.
```
