# Хостинг в Yandex Cloud — пошагово

Как поднять «Цифровой двойник ОПС» на виртуальной машине Yandex Cloud и получить
адрес, который остаётся рабочим при выключенном ноутбуке. Общие сведения о
развёртывании и проверке — [deployment.md](deployment.md); здесь только конкретная
площадка и порядок действий.

Время: 30–40 минут, из них половина — ожидание первой сборки образа.

## Что уже проверено локально

22.09 образ собран и прогнан целиком на Docker 29.1.3 с Compose 2.40.3 (WSL, Ubuntu
24.04) — то есть ровно тем же способом, каким он поднимется на машине:

- `docker compose up --build -d` — сборка проходит, контейнер `Up (healthy)`;
- `/api/health` → `{"status":"ok","llm":{"configured":true,"provider":"deepseek-via-yandex-ai-studio"}}`,
  корень отдаёт редактор (200 `text/html`);
- **живая модель из контейнера отвечает** — запрос к ассистенту прошёл за 23 с;
- `DEPLOY_URL=… npx playwright test tests/e2e/deployment.spec.ts` — 5 passed.

Не проверено, потому что проверяется только на месте: создание ВМ, группа
безопасности и сам скрипт `deploy-vm.sh` на чистой Ubuntu.

## Что получится

Одна виртуальная машина с публичным IP, на ней один Docker-контейнер: он отдаёт и
редактор, и `/api`. Адрес вида `http://<IP>:8080` — его и указываем жюри.

HTTPS в этом варианте нет. Для сдачи это допустимо (сервис внутренний, данные
синтетические), но если нужен HTTPS без возни с сертификатом — см. «Вариант со
Serverless Containers» в конце.

## Перед началом проверьте три вещи

Всё — в [консоли](https://console.yandex.cloud/), эти пункты за вас никто не увидит:

1. **Платёжный аккаунт активен.** Биллинг → статус не «приостановлен» и не «пробный
   период истёк». Иначе ВМ не создастся, а уже созданная остановится.
2. **Квоты фолдера.** Compute Cloud → «Квоты»: должны быть свободны хотя бы 2 vCPU,
   4 ГБ RAM и **один публичный IP-адрес**. Нулевая квота на публичные адреса —
   частая причина «всё создалось, а зайти некуда».
3. **Фолдер тот же, что у ключа модели.** В нашем `LLM_MODEL` folder ID уже прописан;
   если разворачиваете в другом фолдере, ключ AI Studio всё равно продолжит работать —
   он привязан к своему фолдеру, а не к машине.

## Шаг 1. Создать виртуальную машину

Консоль → нужный фолдер → **Compute Cloud** → **Виртуальные машины** → **Создать ВМ**.

| Поле | Значение | Почему так |
|---|---|---|
| Операционная система | **Ubuntu 24.04 LTS** | В её репозиториях есть `docker-compose-v2` 2.24.6, а нашему `compose.yaml` нужен Compose ≥ 2.24 (длинный синтаксис `env_file`) |
| Платформа | любая доступная | Нагрузки нет |
| vCPU | 2, доля vCPU **100 %** | На 20 % первая сборка образа идёт очень долго |
| RAM | **4 ГБ** | Образ собирается на самой машине: `npm ci` плюс сборка SPA. На 2 ГБ сборка падает по памяти |
| Диск | 20 ГБ SSD | Образ, слои Docker и зависимости |
| Публичный адрес | **Автоматически** | Без него машина недоступна снаружи |
| Доступ → Логин | например `ubuntu` | Он же понадобится для SSH |
| Доступ → SSH-ключ | вставить **публичный** ключ (`~/.ssh/id_ed25519.pub`) | Приватный ключ не вставлять никуда никогда |
| Резервное копирование | **выключить** | Cloud Backup требует установки агента и тарифицируется, а сервису нечего резервировать: состояния он не хранит, планы лежат в файлах пользователя |

Ключа нет — создать на своей машине:

```bash
ssh-keygen -t ed25519 -C "pochtatex-deploy"
```

Показать публичный ключ, чтобы скопировать в консоль:

```bash
cat ~/.ssh/id_ed25519.pub
```

Нажать **Создать ВМ**, дождаться статуса `RUNNING` и записать **публичный IPv4** со
страницы машины.

## Шаг 2. Проверить порт 8080

Группа безопасности, которую Yandex Cloud создаёт сам (`default-sg-…`, её назначают
машине, если своей не выбрали), **разрешает весь входящий и исходящий трафик** — 22 и
8080 уже открыты, и делать ничего не нужно. Проверить: Virtual Private Cloud →
**Группы безопасности** → своя группа → **Правила**.

Обратная сторона: машина открыта наружу целиком, и документация Yandex Cloud сама
советует для ресурсов с публичным адресом заводить свою группу и разрешать только
нужное. Для демонстрации жюри это приемлемо — сервис и так открыт по ссылке без
пароля, а данные синтетические.

Если правил нет или группа своя и ограничивающая (группа **без правил блокирует
всё**), добавьте входящее правило:

| Поле | Значение |
|---|---|
| Описание | `editor` |
| Диапазон портов | `8080` |
| Протокол | `TCP` |
| Назначение | `CIDR` |
| CIDR | `0.0.0.0/0` |

Тогда же добавьте **22/TCP** для SSH и разрешающее **исходящее** правило
(`0.0.0.0/0`, все порты): без него машина не скачает пакеты и не достучится до API
модели.

## Шаг 3. Зайти на машину

```bash
ssh ubuntu@<публичный IP>
```

## Шаг 4. Положить на машину исходники

Два способа, оба нормальные.

**A. Архивом со своей машины** — не требует складывать доступы к GitLab на облачную
машину, поэтому предпочтительнее.

На своей машине **обязательно из корня репозитория**: `git archive`, запущенный из
подкаталога, кладёт в архив только его содержимое, и на машину уезжает, например,
один каталог `docs` без `Dockerfile` и `compose.yaml` (проверено 22.09 — так и
вышло).

```bash
cd C:\Users\<пользователь>\PycharmProjects\Pochtatex
```

```bash
git archive --format=tar.gz -o C:\tmp\ops.tar.gz HEAD
```

Проверить, что в архиве весь проект, а не один каталог — в списке должны быть
`compose.yaml` и `Dockerfile`:

```bash
tar -tzf C:\tmp\ops.tar.gz | more
```

```bash
scp C:\tmp\ops.tar.gz ubuntu@<публичный IP>:~
```

Дальше на самой машине:

```bash
mkdir -p ~/ops-digital-twin && tar -xzf ~/ops.tar.gz -C ~/ops-digital-twin && cd ~/ops-digital-twin
```

**B. Клоном из GitLab** — удобнее, если потом обновлять на месте:

```bash
git clone https://git.codenrock.com/<путь-к-репозиторию>.git ops-digital-twin && cd ops-digital-twin
```

## Шаг 5. Создать `.env` с ключом модели

Файл создаётся **на машине руками** и в git не попадает никогда.

```bash
nano .env
```

Вписать значения — те же, что в рабочем локальном `.env`; ключ взять оттуда:

```
LLM_PROVIDER=deepseek-via-yandex-ai-studio
LLM_ENDPOINT=https://llm.api.cloud.yandex.net/v1/chat/completions
LLM_MODEL=gpt://<folder_ID>/deepseek-v4-flash
LLM_API_KEY=<ключ>
LLM_TIMEOUT_MS=60000
LLM_MAX_OUTPUT_TOKENS=4000
ADVICE_RATE_LIMIT=300
ADVICE_RATE_WINDOW_MS=60000
```

`HOST` и `PORT` сюда писать не нужно: их задаёт `compose.yaml`, иначе скопированный
`HOST=127.0.0.1` сделает контейнер недоступным снаружи.

Без `.env` сервис тоже поднимется — ассистент будет считать сам и помечать ответ
«без LLM». Для сдачи это хуже, но не поломка.

## Шаг 6. Запустить

```bash
bash scripts/deploy-vm.sh
```

Скрипт ставит Docker, собирает образ, поднимает контейнер и ждёт, пока
`/api/health` ответит. Первая сборка — несколько минут.

Ожидаемый хвост вывода:

```
Ответ /api/health: {"status":"ok","llm":{"configured":true,"provider":"deepseek-via-yandex-ai-studio"}}
Модель настроена.
```

`"configured":false` означает, что `.env` не подхватился — проверьте, что он лежит
рядом с `compose.yaml`.

Руками то же самое:

```bash
sudo apt-get update && sudo apt-get install -y docker.io docker-compose-v2
```

```bash
sudo docker compose up --build -d && curl http://127.0.0.1:8080/api/health
```

## Шаг 7. Проверить снаружи

С **своей** машины, не с ВМ:

```bash
curl http://<публичный IP>:8080/api/health
```

```bash
DEPLOY_URL=http://<публичный IP>:8080 npx playwright test tests/e2e/deployment.spec.ts
```

Сценарий открывает редактор по адресу деплоя, проверяет health, прямую ссылку, ответ
ассистента и путь «открыть план → сохранить». Ожидается `5 passed`. Затем откройте
адрес в браузере и пройдите сценарий проверяющего руками: загрузить `demo/before.json`,
изменить, сохранить, открыть заново.

## Шаг 8. Вписать адрес в материалы сдачи

Адрес заменяет `TBD` в трёх местах:

- `README.md` — раздел с адресом сервиса и сведениями для доступа;
- `docs/deployment.md` — строка «Адрес рабочего сервиса для жюри»;
- `docs/submission.md` — комплект сдачи.

Сведения для доступа: логина и пароля нет, сервис открыт по ссылке — так и написать.

## Эксплуатация

Состояние контейнера, должно быть `Up (healthy)`:

```bash
sudo docker compose ps
```

Что произошло:

```bash
sudo docker compose logs --tail=50
```

Обновить до свежего `main` (при способе Б из шага 4):

```bash
git pull && sudo docker compose up --build -d
```

Контейнер поднят с `restart: unless-stopped` — перезагрузку машины переживает сам.

**Машину не удалять и не останавливать после сдачи:** проверять будут позже, а до
какой даты сервис должен быть доступен, организаторы не сообщили (открытый вопрос в
`HANDOFF.md`).

## Частые грабли

| Симптом | Причина | Что делать |
|---|---|---|
| `curl` с чужой машины висит, с самой ВМ работает | Закрыт входящий 8080 | Шаг 2 |
| Сборка падает с `killed` или нехваткой памяти | 2 ГБ RAM | Увеличить до 4 ГБ |
| `unknown keyword env_file.path` | Compose старее 2.24 | Ubuntu 24.04 или репозиторий Docker |
| Контейнер поднялся, но снаружи пусто | В `.env` попал `HOST=127.0.0.1` | Убрать `HOST` из `.env` |
| `"configured":false` при живом ключе | `.env` не рядом с `compose.yaml` | Положить рядом и поднять заново |
| `PORT=80` — контейнер падает | Процесс работает от пользователя `node`, порты ниже 1024 ему недоступны | Оставить 8080 |

## Вариант со Serverless Containers

Если нужен готовый **HTTPS-адрес** вида `https://<id>.containers.yandexcloud.net/`
без сертификатов и без круглосуточной ВМ. Лимиты сервису подходят: таймаут запроса до
часа (нашему ассистенту хватает 60 с), образ до 10 ГБ, до 8 ГБ RAM.

Цена — лишние шаги: собрать образ, запушить в Container Registry, создать контейнер,
задать переменные окружения и **отдельно разрешить публичный вызов** (по умолчанию
контейнер закрыт ролью `serverless-containers.containerInvoker`). В день сдачи это
лишний риск, поэтому основной путь — ВМ.
