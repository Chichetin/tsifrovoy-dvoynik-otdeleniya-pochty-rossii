# Развёртывание сервиса

Как поднять «Цифровой двойник ОПС» на чистой машине с Linux и Docker, как проверить,
что он действительно работает, и что в нём заведомо не сделано.

**Адрес рабочего сервиса для жюри — `TBD`:** хостинг ещё не выбран (блокер в
[HANDOFF.md](../HANDOFF.md)). Всё, что нужно для развёртывания, готово: образ, compose и
проверка ниже прогнаны локально, адрес подставляется в README, когда площадка известна.

## Что понадобится

- Linux-хост, Docker ≥ 24 с плагином Compose (проверялось на Docker 29.7.2,
  Docker Compose 5.5.1).
- Доступ в интернет на время сборки: образ ставит зависимости из npm.
- Ничего больше: Node.js, npm и браузеры на хосте не нужны — всё внутри образа.

## Запуск

```bash
git clone <URL репозитория> ops-digital-twin
cd ops-digital-twin
docker compose up --build -d
```

Первая сборка занимает несколько минут (установка зависимостей, сборка SPA и сервера),
повторные — секунды за счёт слоёв Docker. Дальше:

```bash
docker compose ps                        # STATUS должен стать "Up ... (healthy)"
curl http://127.0.0.1:8080/api/health    # {"status":"ok","llm":{"configured":false}} — с ключом: {"configured":true,"provider":"…"}
```

Редактор открывается в браузере по адресу <http://127.0.0.1:8080> (на удалённой машине —
`http://<адрес хоста>:8080`). Тот же порт отдаёт и API ассистента: сервис — один
контейнер с одним адресом, отдельного фронтенд-сервера нет.

### Другой порт

Порт 8080 занят — задайте свой одной переменной, она меняет и публикацию, и порт внутри
контейнера:

```bash
PORT=8081 docker compose up --build -d
curl http://127.0.0.1:8081/api/health
```

## Проверка развёрнутого сервиса

Ручной осмотр заменяется браузерным сценарием: он открывает редактор по адресу деплоя,
проверяет health, прямую ссылку, ответ ассистента без ключа и путь «открыть план →
сохранить». Запускается с машины, где есть Node ≥ 22.12 (это машина разработчика, а не
хост деплоя):

```bash
npm ci
npx playwright install chromium
DEPLOY_URL=http://127.0.0.1:8080 npx playwright test tests/e2e/deployment.spec.ts
```

`DEPLOY_URL` обязателен и может указывать на любой адрес, в том числе на удалённый хост.
Правило одно: переменная задана — проверяют конкретный деплой, и недоступный адрес валит
тесты; переменной нет (обычный `npm run test:e2e`, прогон в CI без Docker) — тесты
пропускаются с причиной и в сеть не ходят. Адреса по умолчанию нет намеренно: с ним
прогон цеплялся к любому процессу на порту 8080 — например, к `npm run serve` из
README — и проверял деплой по dev-сборке.

Прогон на 17.09.2026 против локального контейнера: `5 passed`; тот же файл без
`DEPLOY_URL` — `5 skipped`.

## Переменные окружения

Сервис работает без единой переменной. Всё, что можно задать, задаётся через `.env`
рядом с `compose.yaml` — этот файл в git не попадает (`.gitignore`), в образ не
копируется (`.dockerignore`) и подключается только как окружение контейнера. Шаблон со
всеми переменными и комментариями — [`.env.example`](../.env.example).

```bash
cp .env.example .env     # затем вписать свой ключ провайдера
docker compose up -d     # перечитывает .env
```

| Переменная | Зачем | Без неё |
|---|---|---|
| `LLM_PROVIDER`, `LLM_ENDPOINT`, `LLM_MODEL`, `LLM_API_KEY` | объяснения ассистента от модели (Qwen, DeepSeek, GigaChat, YandexGPT) | ассистент считает рекомендации сам и помечает ответ «Без LLM» — штатный режим, а не ошибка |
| `LLM_TIMEOUT_MS`, `LLM_MAX_OUTPUT_TOKENS` | предел ожидания и длины ответа модели | 20 000 мс и 800 токенов |
| `ADVICE_RATE_LIMIT`, `ADVICE_RATE_WINDOW_MS` | защита баланса: сколько обращений к модели в окно | 30 запросов в минуту на процесс |
| `PORT` | порт наружу и внутри контейнера | 8080 |

`HOST` и `STATIC_DIR` внутри контейнера задаёт `compose.yaml` и `Dockerfile`
(`0.0.0.0` и `/app/dist`); значения из `.env` для них намеренно перекрываются — иначе
скопированный из `.env.example` `HOST=127.0.0.1` сделал бы контейнер недоступным снаружи.

Ключ провайдера в образе не хранится: он попадает в процесс переменной окружения при
запуске. Логи сервера печатают провайдера и модель, но не ключ.

## Обновление

```bash
git pull
docker compose up --build -d     # пересобрать и заменить контейнер
docker compose logs -f app       # смотреть журнал
docker compose down              # остановить и удалить контейнер
```

Состояния на диске у сервиса нет, поэтому обновление — это всегда «пересобрать и
перезапустить»; терять нечего, миграций нет.

## Что внутри образа

Многоступенчатая сборка (`Dockerfile`):

1. Ступень `build` на `node:22-alpine`: `npm ci`, затем `npm run build`
   (`tsc --noEmit` + `vite build` → `dist/`) и `npm run build:server`
   (`vite build --ssr` → `build/server/main.js`). Сломанные типы валят сборку образа.
2. Ступень `runtime` на том же `node:22-alpine`: только `npm ci --omit=dev`, собранный
   SPA и один файл сервера. Исходников TypeScript, тестов, документации и материалов
   организаторов в образе нет — контекст сборки ограничен `.dockerignore`, который
   запрещает всё и открывает поимённо `src`, `server`, `data`, `demo/*.json`,
   `index.html` и конфиги. Демо-планы сдачи (`demo/*.json`, пакет E01) открыты именно
   поэтому: клиент подключает их на сборке, и без них `vite build` в образе упал бы.
3. Процесс запускается от пользователя `node` (не root), слушает `0.0.0.0:$PORT`, имеет
   `HEALTHCHECK` на `/api/health`.

Размер образа на 17.09.2026: 322 МБ на диске (70,8 МБ в реестре), из них ~75 МБ —
production-зависимости по слоям образа, 1,5 МБ — собранный SPA, 119 КБ — сервер.
После переноса клиентских библиотек в `devDependencies` (D-116, 18.09) чистая
установка `npm ci --omit=dev` по `du -sh node_modules` весит 29 МБ вместо 65
(замер тем же способом на `origin/main` до переноса; число по слоям образа
считается иначе и ещё не пересчитывалось — образ после переноса не пересобирался).

Сервер написан на TypeScript и в разработке запускается через `tsx`, но `tsx` —
devDependency, и тащить весь dev-набор в runtime ради него незачем. Поэтому сервер
собирается тем же Vite в один ESM-файл, а пакеты из `dependencies` остаются внешними
(решение D-090).

### Собрать образ без compose

Registry у команды нет, и CI образ не собирает (см. `.gitlab-ci.yml`). Руками:

```bash
docker build -t ops-digital-twin:local .
docker run -d --name ops-digital-twin -p 8080:8080 -e HOST=0.0.0.0 -e PORT=8080 \
  ops-digital-twin:local
```

С ключом провайдера — добавить `--env-file .env`; без него сервис работает в режиме
«без LLM».

Если появится registry, образ публикуется обычным `docker tag` + `docker push`; отдельная
стадия в CI добавляется одним job'ом с `docker login` по переменным проекта.

## Известные ограничения

- **CI на GitLab хакатона не выполняется: у проекта нет раннера.** Проверено по API
  18.09: ни одного успешного pipeline за всё время, у каждого job `runner: null` и
  `failure_reason: stuck_or_timeout_failure` — команды из `.gitlab-ci.yml` ни разу не
  запускались. Бейдж «failed» на коммитах — следствие таймаута ожидания раннера, а не
  красных тестов. Единственная проверка перед merge — локальный прогон в worktree
  (typecheck, lint, unit, build, e2e), его делают `builder` и `integrator` по GIT.md.
  Конвейер оставлен: он заработает без правок, если организаторы подключат раннер или
  команда зарегистрирует свой (`Settings → CI/CD → Runners`, нужны права maintainer).

- **HTTPS нет.** Контейнер отдаёт HTTP. Для внешнего адреса нужен обратный прокси
  (nginx, Caddy, Traefik) с сертификатом — в этот репозиторий он не входит.
- **Аутентификации нет:** кто открыл адрес, тот и редактирует. Сервис рассчитан на
  показ жюри и внутреннего заказчика, не на публичный интернет.
- **Постоянного хранилища нет.** План живёт в браузере и в JSON-файлах, которые
  пользователь сохраняет и открывает сам. Контейнер ничего не пишет на диск, тома не
  нужны, перезапуск ничего не теряет и ничего не помнит.
- **Один процесс, без масштабирования.** Реплик, балансировщика и очередей нет; предел
  нагрузки — предел одного Node-процесса на раздаче статики и расчёте рекомендаций.
- **Только Linux/amd64 проверен.** Сборка на arm64 должна работать (в lockfile есть
  бинарники rolldown под arm64-musl), но не проверялась.
- **Клиентские зависимости из runtime-образа убраны (D-116).** В `dependencies` теперь только `fastify`, `@fastify/static`, `zod` и `polyclip-ts` — ровно то, что импортирует `build/server/main.js`; `three`, `react`, `react-dom`, `react-konva`, `konva`, `zustand` живут в `devDependencies` и в runtime-ступень не попадают. Проверено чистой установкой `npm ci --omit=dev` (29 МБ) и запуском сервера с неё: `/api/health` и SPA отвечают. Основной вес образа по-прежнему базовый `node:22-alpine`.
- **Логи — в stdout контейнера** (`docker compose logs`), ротацию и сбор настраивает
  хост.
