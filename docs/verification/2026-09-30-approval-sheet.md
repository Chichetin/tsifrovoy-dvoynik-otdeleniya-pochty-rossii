## Поведение

Кнопка «Лист согласования…» стоит рядом со «Сравнить с файлом…» в панели «Ассистент →
Эффект изменений» (`ComparisonPanel`) и открывает модальное окно `ApprovalSheet` —
одностраничный документ, который несут на согласование. База «до» — та же, что у таблицы
«Эффект изменений»: выбранный файл сравнения или `baseline` сессии (`source?.plan ?? baseline`).

Лист содержит:

- **Штамп** — план/отделение (`after.name`), источник «до» (имя файла или «состояние при
  открытии или сохранении»), дата на момент открытия листа, поле «Автор» — вводит
  пользователь, по умолчанию пусто.
- **Картинки «до» и «после»** — тот же SVG-экспорт, что и «Экспорт → SVG»
  (`persistence/plan-svg.renderPlanSvg`), вставлены инлайн (без XML-пролога — он нужен
  только отдельному файлу), все слои принудительно видимы — лист не должен скрывать то,
  что скрыто у автора листа сейчас.
- **Эффект «было → стало»** — площадь помещения, занято, свободно, объектов в
  инвентаризации, ошибок и предупреждений проверки.
- **Находки проверки: устранены / появились** — `validatePlan(до)`/`validatePlan(после)`,
  сопоставленные по `code`+`refs` (не по тексту сообщения).
- **Показатели по правилам «было → стало»** — числа `data/catalog/rules.json` для правил,
  которых касается хотя бы одна находка: количество через `countInZoneScope`
  (`domain/inventory`), расстояние до входа через `openingCentre`+`segmentLength`
  (`domain/geometry`) без порога — тот же расчёт, что использует сама проверка. У каждой
  строки свой источник правила (материалы организаторов / допущение команды).
- **Изменения по названиям** — `buildPlanComparison(...).changes`: «Добавлен/Удалён/
  Перемещён: <название>», `id` — мелким текстом рядом, а не в заголовке строки (на бумаге
  нет наведения мышью для раскрытия/`title`, как у id в основном интерфейсе после #10).
- **Допущения расчёта показателей** — `assumptions`/`limitations` детерминированного
  `comparePlans` (сценарий `compare`, без LLM), с пометкой «Допущения расчёта показателей —
  решение команды, не норматив Почты России» — только про сам расчёт (что не суммируется
  дважды), не про правила комплектования и расстояния: у них теперь свой источник в
  таблице выше.

Печать — кнопка «Печать / Сохранить как PDF» вызывает `window.print()`; PDF получают
через диалог печати браузера, отдельная PDF-библиотека не добавлена (запрещена задачей).
`ApprovalSheet.tsx` рендерится через `createPortal(..., document.body)` (D-328): печать
сводится к одному `body > *:not(.approval-sheet) { display: none }`, лист укладывается в
одну страницу A4 (детали — в разделе ревью ниже).

Для планов с разными `id` список изменений, находки и показатели по правилам заменяются
тем же предупреждением, что в «Эффект изменений»: «Файлы имеют разные ID планов…», без
придуманных переносов.

## Ревью !319 (30.09) — два блокера и полировка

**Блокер 1 — числа `demo/effect.md`, которых не было.** Первая версия читала критерий #35
узко: список изменений по названиям + метрики `buildPlanComparison`. Расстояние терминала
до входа (6,62 → 2,25 м) и оба правила комплектования (скамьи 1 → 2, табло 2 → 1) на лист
не попадали. Ревью показало, что код для этих чисел уже есть — `validatePlan`,
`countInZoneScope`, `openingCentre`/`segmentLength` — и его нужно переиспользовать, а не
признавать недостижимым. Добавлено в `src/domain/plan-comparison.ts` (домен, не фича:
`features/assistant` не может импортировать `domain/inventory`/`domain/validation`
напрямую — граница `no-restricted-imports` считает их «соседними features» из-за
одноимённых `src/features/inventory`/`src/features/validation`; лечится только
переносом логики в domain, где такого совпадения нет):

- `issueDeltas` — находки `validatePlan`, сопоставленные по `code`+`refs` между «до» и
  «после»: что устранено, что появилось.
- `ruleEffects` — числа правил, которых касается хотя бы одна находка, «было → стало»
  на обеих сторонах (не только когда правило нарушено): `countInZoneScope` для правил
  комплектования, `openingCentre`+`segmentLength` (без порога) для расстояния до входа —
  ровно те примитивы, на которых стоит сама проверка (`src/domain/validation` не
  тронут). У каждой строки — `source`/`sourceNote` конкретного правила.

`buildPlanComparison` меняется только добавлением: существующие поля/тесты не менялись,
5/5 ручных мутаций новых функций поймал `tests/plan-comparison.test.ts` (см. «Мутации»).

**Блокер 2 — общая пометка приписывала команде правило организаторов.** До ревью один
`RULE_NOTE` («решение команды, не норматив Почты России») стоял под всем блоком
допущений; после добавления `ruleEffects` он лёг бы и под строку `rule_queue_terminal_entrance`
(материалы организаторов, не команда). Исправлено: у каждой строки таблицы «Показатели по
правилам» — свой `sourceNote` (тот же текст, что `ruleNote` в `src/domain/validation`);
общая пометка осталась только под допущениями `comparePlans` (как считается площадь) —
её текст сужен до «Допущения расчёта показателей…», без слова «правила».

**Печать A4 — два блокера в одном.** `page.pdf({ format: 'A4' })` давал 2 страницы, вторая
почти пустая. Причина оказалась двойной:

1. Первая версия печати прятала всё через `visibility: hidden` на `body *` и показывала
   обратно только `.approval-sheet`/потомков. Невидимые предки остаются в потоке
   документа и держат его высоту — а высота холста редактора (`<canvas>`) задаётся
   *пикселями через инлайн-стиль* из `ResizeObserver` (`src/features/editor`), который
   никакой класс в таблице стилей не может пересилить без борьбы со специфичностью
   против инлайн-атрибута. Исправлено переносом `ApprovalSheet` через `createPortal` в
   `document.body` (D-328): он больше не вложен в `.shell`, и печать одним правилом
   `body > *:not(.approval-sheet) { display: none !important; }` убирает `#root`
   целиком из потока, без исключений и специфичности.
2. Даже после этого собственный контент листа (картинки плана, три таблицы, три списка)
   был выше одной страницы A4 при обычных полях печати Chromium. Печатная вёрстка
   уплотнена в `@media print`: картинки плана — фиксированная высота `32mm` (было —
   по ширине панели, что растягивало их непропорционально высоко), поля таблиц/списков
   и отступы между секциями меньше, чем на экране.

Проверено не «высотой на экране», а самим PDF: `tests/e2e/approval-sheet.spec.ts`
запускает `page.pdf({ format: 'A4' })` и считает объекты `/Type /Page` (не `/Type
/Pages`) в сырых байтах файла — без внешней библиотеки разбора PDF. Локально
дополнительно собран и открыт `pdftoppm`'ом реальный PDF демо-пары — 1 страница, весь
контент читаем (артефакт не коммитился, только `docs/verification/2026-09-30-approval-sheet/*.png`
из Playwright-скриншотов состояния `@media print` на экране).

**Полировка (не блокер).** Серый фон `body` под листом и рамка/синяя обводка фокуса поля
«Автор» в печати убраны (`html, body { background: none }`, `.approval-sheet__facts input
{ border: none; outline: none }`); проверено `toHaveCSS` в e2e. Решение показывать `id`
в скобках мелким текстом (а не в раскрытии/`title`, как в основном интерфейсе после #10)
зафиксировано одной строкой в D-326 — на печатной странице нет курсора для наведения.

Обновлены D-326 (место кнопки + решение про id), D-327 (снята узкая формулировка критерия,
описан фактический охват находок и правил), D-328 (портал вместо `visibility`-трюка,
причина и что именно уплотнено в печати).
