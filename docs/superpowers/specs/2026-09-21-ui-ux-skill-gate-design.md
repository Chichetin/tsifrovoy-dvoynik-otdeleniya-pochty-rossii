# Спецификация: обязательный UI/UX quality gate

Дата: 2026-09-21
Статус: согласованный дизайн, внедряется в правила проекта

## Цель

Каждая UI-фича должна быть проверена не только тестом кода, но и глазами
пользователя в реальном браузере. До написания кода агент получает устойчивое
визуальное решение, после написания — воспроизводимое доказательство поведения,
скриншоты и проверку доступности.

## Область действия

UI-фича — это новая или изменённая страница, панель, компонент, визуальный стиль,
интеракция, состояние загрузки/ошибки, responsive-поведение или сценарий в
браузере. Протокол действует для builder и для любой самостоятельной правки
интерфейса в рабочем worktree.

Чистые изменения domain, сервера, документации и тестовых фикстур без изменения
пользовательского интерфейса под этот gate не попадают. Если граница сомнительна,
применяется UI-протокол.

## Матрица скиллов

| Этап | Скиллы | Минимальный результат |
|---|---|---|
| До кода | `ui-ux-pro-max`, `frontend-design` | краткий UI-бриф: пользовательская задача, состояния, иерархия, типографика/цвет, интеракции, целевые viewports и критерии готовности |
| Исследование в браузере | `playwright-interactive`, `webapp-testing`, `playwright` | приложение открыто на реальном dev-стенде; пройден целевой путь и зафиксированы наблюдения, консоль и сетевые ошибки |
| Детерминированная проверка | `webapp-testing`, `playwright` | существующая e2e-спека обновлена или добавлена; минимум для редактора — «открыть → загрузить демо → изменить → сохранить → открыть заново» |
| Визуальное доказательство | Playwright-снимок; `screenshot` — для снимка всего рабочего стола/окна, если это требуется | до четырёх снимков состояния «после» с вырезанной областью (`clip`), целевым viewport и понятным именем в `docs/verification/` |
| Доступность | `accessibility-scan`, `accessibility-inspect` | automated-скан live DOM и ручной проход клавиатуры, focus order, имён/ролей/состояний, zoom/reflow; findings привязаны к URL/селектору или отмечены как human-required |
| Финальный review | `web-design-guidelines` | проверка визуальной и интеракционной целостности; найденные проблемы исправлены либо записаны как явное ограничение |

## Условные скиллы

- `accessibility-diff` обязателен при изменении существующей страницы, если для
  неё есть baseline; он должен показать отсутствие новых нарушений.
- `accessibility-fix` запускается при найденном нарушении, а затем scan/inspect
  повторяются. Он не заменяет ручное решение для контекстных или визуальных
  проблем.
- `accessibility-audit` нужен для multi-page фичи, крупного UI-пакета, release
  gate или проверки всего продукта; для одной страницы достаточно scan + inspect.
- `playwright-trace` нужен при падении, флейке, таймауте, неожиданном сетевом
  запросе или расхождении между exploratory и deterministic прогоном.
- `screenshot` не подменяет Playwright-снимок страницы: он применяется, когда
  нужно доказать состояние окна/рабочего стола или Playwright недоступен.

## Артефакты и правило готовности

В `HANDOFF.md` для UI-фичи указываются:

1. скиллы из матрицы и их роль в работе;
2. URL/маршрут, viewport и пользовательский сценарий;
3. команды и фактический результат unit/e2e/a11y-проверок;
4. пути к снимкам, trace и отчётам;
5. найденные проблемы, применённые fixes и оставшиеся ограничения.

Фича считается готовой только когда детерминированный браузерный сценарий,
минимальный снимок, scan, inspect и финальный UI-review имеют зелёный результат
или явно оформленное ограничение. Нельзя писать «проверено», если нет команды и
артефакта. Снимки не должны содержать реальные персональные данные — только
синтетические планы проекта.

Если нужный скилл или браузерный runtime недоступен, агент может продолжить
исследование через ближайший fallback, но обязан записать это в `HANDOFF.md` и
не имеет права объявлять UI-фичу полностью принятой до закрытия пропуска.

## Владение

Builder отвечает за UI-бриф, реализацию и первичные артефакты. `qa` повторяет
детерминированный путь на свежем `main`, `operator` проверяет сценарий роли и
снимки, reviewer проверяет наличие gate в diff. Интегратор не принимает MR без
записи о gate или явного блокера для человека.
