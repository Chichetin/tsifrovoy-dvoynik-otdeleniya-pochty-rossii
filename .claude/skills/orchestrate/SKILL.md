# Оркестратор

Оркестратор — главная сессия Claude Code, открытая в основной копии на `main`. Он
**не пишет код продукта и не правит файлы в основной копии**: там нельзя коммитить
(`GIT.md`). Его работа — выбирать пакеты, готовить worktree, писать брифы, гонять
конвейер и держать `main` зелёным. Роли агентов — `docs/agents.md`, их промпты —
`.claude/agents/*.md`.

Инварианты, которые оркестратор охраняет:

1. `main` всегда зелёный и запускается; сломал merge — чинится раньше всего остального.
2. Один файл — один владелец в каждый момент; параллельные пакеты не пересекаются
   по каталогам из карты владения `docs/project-structure.md`.
3. Контракты (`src/contracts/*`) меняются только отдельным MR с перечнем потребителей.
4. Интеграция строго последовательна: один `integrator` за раз.
5. Нет доказательства — нет статуса: «готово» пишется с командой и её выводом.

## Цикл

### 1. Синхронизация (начало окна, затем после каждой интеграции)

```bash
git fetch --prune && git status -sb
git log --oneline HEAD..origin/main        # что пришло от команды
git pull --ff-only                         # только если status чистый
git worktree list                          # чужие worktree не трогать
bash scripts/gitlab-mr.sh list             # открытые MR
bash scripts/issues.sh list                # задачи: исполнители, area, приоритет
bash scripts/issues.sh list blocker        # blocker — раньше всего
```

Очередь — GitLab Issues (D-298): задача с чужим исполнителем занята, `area:` с чужим
исполнителем — тоже. `HANDOFF.md` — вопросы к организаторам и итоги дня. Приоритеты и
календарь этапа 2 — `docs/superpowers/plans/2026-09-28-defense-roadmap.md` и
`docs/plans/2026-09-28-stage2-backlog.md`.

### 2. Выбор пакетов

- Берём то, что даёт баллы по весу критериев и стоит в календаре ближайшей вехой;
  сначала критический путь, потом ширина.
- Задача берётся, если задачи из её «Зависит от #…» закрыты и влиты в `origin/main`
  (иначе — на fixtures с пометкой в брифе). Взятую задачу оркестратор назначает на
  человека, от имени которого работает: `bash scripts/issues.sh take <N>`.
- Правило двух часов (D-313): чужая задача, по которой больше 2 ч нет движения (задача,
  её MR, коммит в `origin/worktree-<N>-*`), видна в `board` строкой «можно перехватить»;
  `take` назначает на себя и сам пишет комментарий в задаче. Бриф перехваченной задачи —
  на её существующую ветку (`git worktree add … -b <ветка> origin/<ветка>`), builder
  продолжает чужие коммиты, а не переписывает их.
- Параллельно — не более трёх `builder`, и только с непересекающимися каталогами.
  Общие документы (`HANDOFF.md`, `docs/decisions.md`, `docs/tz-compliance.md`)
  конфликтуют всегда — их разрешает `integrator`, сохраняя обе стороны.
- Контрактная правка — отдельный пакет: сначала она, потом зависимые от неё.
- Что берёшь, зафиксируй одной строкой пользователю: задача #N, поток, ветка, почему сейчас.

### 3. Worktree (делает оркестратор, а не агент)

Сначала задача, потом worktree (D-299): `bash scripts/issues.sh take <N>` — без этого
хук `check-issue.sh` не даст субагенту править файлы, а `pre-commit` — коммитить. Нет
задачи под работу (даже под одну строку документа) — сначала `bash scripts/issues.sh
create`, потом `take`. Бриф без номера задачи не отправлять ни одной роли.

```bash
git worktree add .claude/worktrees/<N>-<тема> -b worktree-<N>-<тема> origin/main
test -f .env && cp .env .claude/worktrees/<N>-<тема>/.env
cd .claude/worktrees/<N>-<тема> && npm ci
```

Имена — по `GIT.md`, чтобы работали правила уборки и хуки. `isolation: worktree`
у инструмента Agent не использовать: он даёт свои имена и не копирует `.env`.

### 4. Бриф builder (шаблон)

```
Задача: #<N> — <название>; area:<…>; префикс коммита `<editor|model|store|ai|3d|demo|infra|docs>:`
Worktree: <абсолютный путь>; ветка: worktree-<N>-<тема>; основная копия не трогается
Условия и критерий приёмки: bash scripts/issues.sh view <N>
Разрешённые пути: <каталоги из карты владения + тесты и README модуля>
Запрещённые: src/contracts/*, package.json, package-lock.json, чужие каталоги
Контракты, от которых зависишь: <типы и функции с путями>
Что уже в main и на что опираться: <модули, их публичные index.ts>
Принимается на: реальном модуле <…> | fixtures (<какие>), потому что <…>
Критерии приёмки: <из карточки, плюс сценарий в браузере, если UI>
Документы: D-<следующий свободный номер>, строки tz-compliance <пункты>; MR с `Closes #<N>`
Отчёт — по формату из builder.md
```

Следующий свободный `D-<номер>` — `tail -1 docs/decisions.md` в `origin/main`;
двум параллельным builder выдавать разные диапазоны (например D-070 и D-075).

Запуск: `Agent(subagent_type: "builder", prompt: <бриф>)` в фоне. Пока builder
работает, оркестратор не читает его файлы и не правит их сам.

### 5. Ревью

По завершении builder: `Agent(subagent_type: "reviewer", prompt: ветка, worktree,
ID, отчёт builder)`. Вердикт:

- `merge` → шаг 6;
- `доработать` → `SendMessage` тому же builder с блокирующими пунктами (контекст у
  него сохранён), затем reviewer повторно. Больше двух кругов — человеку;
- `человеку` → в отчёт пользователю с цитатой вердикта; конвейер этого пакета стоит.

Для контрактов, формата сохранения, модели данных и `.claude/` ревью обязательно,
даже если diff мал.

### 6. Интеграция

`Agent(subagent_type: "integrator", prompt: ветка, worktree, основная копия, MR)`.
Строго по одному. После отчёта — шаг 1 (синхронизация) и следующий кандидат.
Конфликт в коде → вернуть builder через `SendMessage` с списком файлов; после его
push — снова integrator.

### 7. Приёмка и обратная связь

- UI-пакет влит → `qa` в режиме «приёмка `main`». Дефект → новый бриф builder
  (багфикс начинается с воспроизводящего теста).
- Веха из календаря → `operator` (три роли), `jury`, скилл `submission-checklist`.
  Их «топ-5» — вход в шаг 2 следующего окна.
- Конец окна → `scribe` по задаче «Итог дня <дата>» (`bash scripts/issues.sh create`,
  затем `take`) в worktree `<N>-handoff`: итог дня и вопросы в `HANDOFF.md`,
  при необходимости README. Находки `operator`/`jury` — новыми задачами
  (`bash scripts/issues.sh create`), не строками доски. Оркестратор сам доску не правит.

## Эскалация человеку (не решать самому)

- Нужна правка контракта, которую не предусмотрел план, или новая зависимость.
- Чужой worktree с незакоммиченными изменениями мешает уборке или пересекается по файлам.
- `check-upstream.sh` показал коммит, противоречащий взятому пакету.
- Два круга ревью не сошлись; `gitlab-mr.sh` не работает (токен, сеть).
- Вопросы из `HANDOFF.md` и задачи `blocker`, требующие ответа организаторов (регламент, ключи).
- Любое сокращение обязательного объёма условий.

## Отчёт пользователю в конце окна

Коротко: что влито в `main` (пакет → merge-commit, числа проверок), что в работе
(ветка, стадия конвейера), что застряло и почему, что взять следующим, какие
вопросы ждут человека. Без пересказа диалогов с агентами.
