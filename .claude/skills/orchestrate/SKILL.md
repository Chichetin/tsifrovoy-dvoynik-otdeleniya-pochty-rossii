# Оркестратор

Оркестратор — главная сессия Claude Code в основной копии на `main`. Он не пишет код и
не правит файлы в основной копии. Его работа: выбрать задачи, открыть worktree,
написать бриф, вести конвейер, держать `main` зелёным. Роли — `docs/agents.md`.

Инварианты:

1. `main` зелёный и запускается. Сломанный `main` чинится раньше всего.
2. Параллельные задачи не пересекаются по каталогам (`docs/project-structure.md`).
3. Контракт меняется только отдельным MR со списком потребителей.
4. Один `integrator` за раз.
5. «Готово» — только с командой и её выводом.

## Цикл

### 1. Синхронизация (начало окна и после каждого merge)

```bash
git fetch --prune && git status -sb
git log --oneline HEAD..origin/main        # что пришло от команды
git pull --ff-only                         # только если status чистый
git worktree list                          # чужие worktree не трогать
bash scripts/gitlab-mr.sh list             # открытые MR
bash scripts/issues.sh list blocker        # blocker — раньше всего
bash scripts/issues.sh board               # исполнители, area, кого можно перехватить
```

### 2. Выбор задач

- Бери то, что даёт баллы по весу критериев. Сначала критический путь, потом ширина.
- Задачу бери, если задачи из «Зависит от #…» влиты в `origin/main`. Иначе — на
  fixtures с пометкой в брифе.
- Взять = `bash scripts/issues.sh take <N>` от имени своего человека. Задачи для
  работы нет — `create`, затем `take`.
- Задачу без движения больше 2 ч `take` перехватывает (D-313). Бриф — на её ветку:
  `git worktree add … -b <ветка> origin/<ветка>`.
- Параллельно — до трёх `builder` с непересекающимися каталогами.
- Сообщи человеку одну строку: задача #N, поток, ветка, почему сейчас.

### 3. Worktree

```bash
git worktree add .claude/worktrees/<N>-<тема> -b worktree-<N>-<тема> origin/main
test -f .env && cp .env .claude/worktrees/<N>-<тема>/.env
cd .claude/worktrees/<N>-<тема> && npm ci
```

`isolation: worktree` у инструмента Agent не используй: он даёт свои имена и не
копирует `.env`.

### 4. Бриф builder

```
Задача: #<N> — <название>; area:<…>; префикс коммита `<editor|model|store|ai|3d|demo|infra|docs>:`
Worktree: <абсолютный путь>; ветка: worktree-<N>-<тема>
Условия и критерий приёмки: bash scripts/issues.sh view <N>
Разрешённые пути: <каталоги потока + тесты и README модуля>
Запрещённые: src/contracts/*, package.json, package-lock.json, чужие каталоги
Опора в main: <модули и их index.ts>
Принимается на: реальном модуле <…> | fixtures (<какие>)
```

Запуск: `Agent(subagent_type: "builder", prompt: <бриф>)` в фоне. Пока builder
работает, его файлы не читай и не правь.

### 5. Ревью

`Agent(subagent_type: "reviewer", prompt: ветка, worktree, #N, отчёт builder)`.

- `merge` → шаг 6.
- `доработать` → `SendMessage` тому же builder с блокирующими пунктами, затем снова
  reviewer. Больше двух кругов — человеку.
- `человеку` → человеку с цитатой вердикта. Задача стоит.

Ревью — по размеру diff. Небольшую правку builder проверяет сам, и её сразу
вливает integrator.

### 6. Интеграция

`Agent(subagent_type: "integrator", prompt: ветка, worktree, основная копия, MR)`.
Строго по одному. После отчёта — шаг 1. Конфликт в коде → builder через
`SendMessage`, затем снова integrator.

### 7. Вехи и конец окна

- Веха → `qa` (приёмка `main`), `operator` (три роли), `jury`, скилл
  `submission-checklist`. Их находки — новые задачи (`create`), не строки документов.
- Человек просит объяснить результат → скилл `/explain`.

## Эскалация человеку

- Нужна правка контракта вне плана или новая зависимость.
- Чужой worktree с незакоммиченными правками мешает или пересекается по файлам.
- `check-upstream.sh` показал коммит против взятой задачи.
- Два круга ревью не сошлись. `gitlab-mr.sh` не работает.
- Вопрос к организаторам или `blocker`, который требует их ответа.
- Любое сокращение обязательного объёма условий.

## Отчёт человеку в конце окна

До 5 строк: что влито (задача → merge-commit), что застряло и почему, какие вопросы
ждут человека.
