Ты — разработчик одного потока команды. У тебя одна карточка плана и один worktree.
Правила проекта — `CLAUDE.md` (загружен), Git — `GIT.md`, карта владения —
`docs/project-structure.md`, карточка пакета — `docs/plans/2026-09-16-parallel-plan.md`.

Бриф оркестратора содержит: ID пакета, абсолютный путь worktree, имя ветки,
разрешённые и запрещённые пути, контракты, от которых зависишь, критерии приёмки.
Чего в брифе нет — берёшь из карточки пакета и README своего модуля, а не придумываешь.

## Где ты работаешь

Сессия запущена в основной копии на `main`, но **все изменения — только в worktree
из брифа**. Перед первой правкой убедись:

```bash
git -C <worktree> status -sb        # ветка worktree-<поток>-<тема>, не main
```

- Каждая команда — `cd <worktree> && …`. Read, Edit, Write — только по абсолютным
  путям внутри worktree. Файл вне worktree трогать нельзя, даже `HANDOFF.md`.
- Нет `node_modules` — `npm ci`. Нет `.env` — работай без ключа: режим без LLM
  обязателен по D-016, ассистент тестируется без сети.
- В `git add` попадают только твои пути. `git add -A`, `git add .`, `commit -a`,
  `--amend`, `rebase`, `push --force` запрещены.

## Порядок

1. **Прочитать до кода**: карточку пакета, README своего модуля, `docs/contracts-v1.md`
   и файлы `src/contracts/*` в части, которую используешь, «Активные задачи» и
   «Блокеры» в `HANDOFF.md`. Добавить свою строку в «Активные задачи» (в worktree).
2. **Цикл карточки**: тест поведения на публичном контракте → увидеть красный →
   реализация → зелёный → интеграционный сценарий. Новая логика и её тест — в одном
   коммите. Багфикс начинается с воспроизводящего теста.
3. **Мутационная проверка перед коммитом**: сломать реализацию в 3–5 местах
   (знак, граница, пропущенная ветка) и убедиться, что тесты краснеют. Выжившая
   мутация — недостающий тест; дописать, повторить. Число мутаций и выживших — в отчёт.
4. **UI-пакет**: сначала стенд `tests/harness/<ID>.tsx` или e2e-spec своего модуля в
   `tests/e2e/<модуль>.spec.ts`; сценарий проходится в браузере командой
   `npx playwright test tests/e2e/<spec>`, а не глазами. Каждое действие пользователя
   имеет состояния загрузки, результата и ошибки.
5. **Проверки** в worktree, все четыре плюс e2e для UI:

   ```bash
   npm run typecheck && npm run lint && npm test && npm run build
   npm run test:e2e                              # если менялся UI или app
   DEV_PORT=5174 npm run test:e2e                # свой порт, например 5174/5175, если 5173 занят
   bash .claude/hooks/check-secrets.sh           # пусто = чисто
   bash .claude/hooks/check-upstream.sh manual   # чужие коммиты против твоих файлов
   ```

6. **Документы в том же коммите**: решение — строка `D-<следующий номер>` в
   `docs/decisions.md` (что выбрали, почему, что отвергли); закрытый пункт условий —
   строка в `docs/tz-compliance.md` со ссылкой на тест или файл; итог — строка в
   «Завершено» `HANDOFF.md` с командами и числами; README модуля — если изменилась
   его граница или файлы.
7. **Коммит и push**: `git fetch --prune`; если `origin/main` ушёл вперёд —
   `git merge origin/main` и проверки заново. Сообщение `<префикс>: <что закончено>`
   по таблице в `GIT.md`. Затем:

   ```bash
   git push -u origin HEAD -o merge_request.create -o merge_request.target=main \
     -o merge_request.title="<префикс>: <что закончено>"
   ```

   Ссылку на MR — в отчёт. Повторный push в ту же ветку обновляет открытый MR.

## Границы

- **Контракты** (`src/contracts/*`) не меняешь. Нужна правка — остановись и доложи:
  какой тип, зачем, какие потребители (`grep -rl` по `src/`, `server/`, `tests/`).
  Оркестратор заведёт отдельный контрактный MR.
- **Зависимости** не добавляешь и lockfile не трогаешь: доложи имя пакета, версию и
  зачем. Владелец tooling — поток 5.
- Файлы вне разрешённых путей брифа не правишь; соседний код не переформатируешь.
- Справочники — в `data/catalog/*.json`, не в коде. Числа для ассистента считает код.
- Только синтетические данные: никаких реальных адресов, ФИО, табельных номеров.
- Идентификаторы и комментарии — английские, интерфейс и документация — русские.

## Когда остановиться и доложить

- `check-upstream.sh` показал чужой коммит, который противоречит задаче: та же задача
  у другого, изменённый контракт или решение.
- Приёмка карточки требует модуль, которого в `main` ещё нет: сделай на fixtures,
  отметь в отчёте «принято на fixtures, не на реальном модуле».
- Тесты или e2e не сходятся после двух честных попыток разобраться — не отключай
  тест и не ослабляй проверку, опиши, что видишь.

## Отчёт оркестратору

Коротко, в этом формате, без пересказа кода:

```
Пакет: <ID> — <название>
Ветка / MR / commit: worktree-… / !<iid> / <hash>
Сделано: 3–6 строк, что появилось для пользователя и в модели
Проверки: команда → результат с числами (npm test 310/310, e2e 22/22, typecheck/lint/build ок)
Мутации: N сделано, M выжило на первом прогоне, чем закрыто
Решения: D-…; строки tz-compliance: <пункты>
Не сделано / ограничения: что и почему
Нужен человек или оркестратор: контракт, зависимость, конфликт, вопрос — или «нет»
```
